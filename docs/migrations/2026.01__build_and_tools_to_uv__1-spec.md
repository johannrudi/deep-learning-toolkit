# Spec: Build System and Tools Migration to uv

This document records the end state of the migration from a `setuptools` + `pip` + `bumpver` toolchain to a uv-native one, together with the reasoning behind each decision and the verification performed.

Reference versions: `uv` 0.12.1, `uv_build` 0.12.x, Python 3.11.

## Scope

The migration covers six areas:

1. the PEP 517 build backend (`setuptools` &rarr; `uv_build`);
2. the dependency model (extras &rarr; dependency groups, with a committed lock file);
3. continuous integration (four near-duplicate workflows &rarr; one matrix workflow);
4. publishing (`python -m build` + `pypa/gh-action-pypi-publish` &rarr; `uv build` + `uv publish`);
5. version management (`bumpver` &rarr; `uv version`);
6. project metadata and licensing (GPL-3.0-only &rarr; Apache-2.0, plus `CITATION.cff`).

## 1. Build backend

`pyproject.toml` declares:

```toml
[build-system]
requires = ["uv_build>=0.12.1,<0.13.0"]
build-backend = "uv_build"

[tool.uv.build-backend]
module-name = "dlk"
module-root = ""
```

The `[tool.uv.build-backend]` table is **required**, not cosmetic. `uv_build` defaults to a `src/` layout and derives the module name by normalizing the project name, so it would look for `src/deep_learning_toolkit/__init__.py`. This project keeps a flat layout with a module name (`dlk`) that differs from the distribution name (`deep-learning-toolkit`), so both settings must be overridden. Without them the build fails with a module-not-found error.

Migrating to a `src/` layout was rejected: it would have rippled into `Makefile` (`PACKAGE_DIR`), `[tool.isort] src_paths`, and the `basedpyright` configuration for no functional gain.

Removed: `[tool.setuptools.packages.find]`. Its `include`/`exclude`/`namespaces` semantics are subsumed by the single-module model — the wheel contains exactly the `dlk` directory, so `tests*` and `_*` are excluded structurally rather than by pattern.

`license-files = ["LICEN[CS]E*"]` was retained. `uv_build` uses the PEP 639 reduced portable glob syntax, which supports `[]` character classes.

### Distribution contents

`uv_build` places the following in the sdist: `pyproject.toml`, the module tree under `module-root`, and the files referenced by `project.readme` and `project.license-files`. This is narrower than the previous setuptools sdist — `tests/`, `Makefile`, `docs/`, and `examples/` are no longer included.

`tool.uv.build-backend.source-include` was deliberately **not** set. It would only matter for making an sdist downloaded from PyPI independently testable; CI uses `actions/checkout` and therefore always has the full working tree.

Cleanup: the stale `deep_learning_toolkit.egg-info/` directory (an untracked setuptools artifact) is obsolete.

## 2. uv version pinning

```toml
[tool.uv]
required-version = ">=0.12.1,<0.13"
```

This constrains the **`uv` executable**, and is distinct from `build-system.requires`, which constrains the **`uv_build` backend package**. They are separate PyPI distributions released on the same cadence:

- `build-system.requires` is consumed by any PEP 517 frontend, is published in the sdist metadata, and governs only distribution building.
- `[tool.uv] required-version` is a local and CI guardrail: every uv command in the project fails immediately if the running `uv` falls outside the range. It is not published.

The practical payoff is in CI: `astral-sh/setup-uv` reads `required-version` when no explicit `version` input is given, so CI installs a `uv` from the same range used locally instead of drifting to the latest release.

Note that `uv build` uses the backend copy bundled inside the `uv` binary when it satisfies the `requires` bound, so no network fetch of `uv_build` occurs. Other frontends such as `python -m build` always download the `uv_build` package.

## 3. Dependency model

Development dependencies live in `[dependency-groups]`, published optional dependencies in `[project.optional-dependencies]`:

- group `dev`: `basedpyright`, `black`, `flow-matching`, `isort`, `pytest`, `torch-kde`
- extra `diffusion`: `flow-matching`
- extra `kde`: `torch-kde`

`uv sync` installs the default `dev` group, so a single command yields a fully working formatting, linting, and testing environment. `uv sync --all-extras` adds the published extras.

### Corrections made

- **`pip install -e ".[dev]"` never worked.** `dev` and `test` were declared as dependency groups, not extras, so `pip` rejected them as unknown extras. The old CI workflows all invoked variations of this command. `README.md` and `AGENTS.md` documented it as well.
- **The `test` group was folded into `dev`.** It only contained `pytest`, which `dev` already provides.
- **Removed from `dev`:** `pip-tools` (superseded by `uv.lock`; no `requirements*.txt` exists), `twine` (publishing goes through `uv publish`), `build` (superseded by `uv build`), and `bumpver` (see section 5). Removing `bumpver` also dropped its transitive `lexid` and `toml` dependencies from the lock.

### Lock file

`uv.lock` is committed. CI sets `UV_LOCKED=1`, which makes uv fail rather than silently re-resolve when the lock is stale. Consequently `uv lock` must be run and committed after any dependency change in `pyproject.toml`.

## 4. Continuous integration

Four near-identical workflows (`compile.yml`, `format.yml`, `lint.yml`, `tests.yml`) were replaced by a single `.github/workflows/ci.yml`:

```yaml
name: CI

on:
  push:
    branches: ["main", "next"]
  pull_request:

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

env:
  FORCE_JAVASCRIPT_ACTIONS_TO_NODE24: true
  UV_LOCKED: 1

jobs:
  check:
    name: ${{ matrix.target }} @py${{ matrix.python-version }}
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        python-version: ["3.11"]
        target: [compile, format-check, lint, test]
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v9
        with:
          python-version: ${{ matrix.python-version }}
          enable-cache: true
      - name: Run make ${{ matrix.target }}
        run: make ${{ matrix.target }}
```

### Why the old workflows could not have worked

The `Makefile` drives every tool through `uv run`, but the old workflows installed with `pip` after `actions/setup-python` and never installed `uv`. Every job would have failed with `uv: command not found`. Additionally, `[tool.basedpyright]` sets `venvPath = "."` and `venv = ".venv"`, which cannot resolve under a bare `setup-python` install.

### Design decisions

- **No install step.** `uv run` creates and syncs `.venv` from `uv.lock` on demand, so the separate dependency-installation step was removed entirely.
- **Matrix over make targets.** One job per target, `fail-fast: false` so a formatting failure does not mask a test failure.
- **Python version via `setup-uv`.** The `python-version` input sets `UV_PYTHON`, which overrides both `.python-version` and `requires-python` resolution.
- **Python 3.12 dropped** from the matrix; 3.11 is the `requires-python` floor and the package is pure Python (`py3-none-any`), so a second interpreter added cost without coverage.
- **Caching** via `enable-cache: true`. The default `cache-dependency-glob` already covers `uv.lock` and `pyproject.toml`, which matters because `torch` is a large download.
- **Redundant steps removed.** `lint.yml` and `tests.yml` both ran `make compile` before their real target; `make test` already declares `compile` as a prerequisite, and `compile` is its own matrix job.
- **Job naming.** `${{ matrix.target }} @py${{ matrix.python-version }}` yields `lint @py3.11`. Keeping the interpreter in the name preserves uniqueness if versions are re-added later; GitHub does not disambiguate explicitly-set duplicate job names. These strings are also what branch protection matches on.

### Triggers and duplicate runs

`push` is restricted to `main` and `next`; `pull_request` carries no branch filter and so covers PRs targeting any branch, on the default activity types (`opened`, `synchronize`, `reopened`).

A known consequence: while a PR is open from a branch that is also in the `push` list (`next` &rarr; `main`), each push fires both events with different `github.ref` values (`refs/heads/next` versus `refs/pull/N/merge`). The concurrency group cannot collapse them, because the two events legitimately test the branch tip and the simulated merge result. This was accepted rather than dropping `next` from `push`, so that pushes to `next` are checked even when no PR is open.

### Badges

The four per-workflow badges collapse into one, because the shields.io `github/actions/workflow/status` endpoint is keyed by workflow file name and reports the whole-run conclusion:

```
[![CI](https://img.shields.io/github/actions/workflow/status/johannrudi/deep-learning-toolkit/ci.yml?style=for-the-badge&label=CI)](https://github.com/johannrudi/deep-learning-toolkit/actions/workflows/ci.yml)
```

Per-job badges remain possible via the `github/check-runs/{user}/{repo}/{ref}?nameFilter=` endpoint, which was verified to work against this repository. It was rejected as fragile: `nameFilter` must match the rendered job name exactly, including the `@py3.11` suffix, and a rename degrades silently instead of failing.

Alternatives considered and rejected for deduplication: a composite action (too little shared surface — only `checkout` plus `setup-uv`) and a reusable `workflow_call` workflow with four thin callers (preserves four badges, but unnecessary once a single badge was acceptable).

## 5. Publishing

`.github/workflows/publish.yml` retains the two-job build/publish split so that the publishing job needs neither a checkout nor repository write scope:

```yaml
on:
  release:
    types: [published]
```

Build job: `actions/checkout` &rarr; `setup-uv` (Python 3.11, cache enabled) &rarr; tag guard &rarr; `uv build --no-sources` &rarr; upload the `dist/` artifact.

Publish job: `actions/download-artifact` &rarr; `setup-uv` &rarr; `uv publish --trusted-publishing always`, with `permissions: id-token: write` and the
`pypi` deployment environment.

### Decisions

- **The tag-push trigger was removed.** Previously both `release: [published]` and `push: tags: v*` were configured. The normal flow (push tag, then publish a release from it) fired both, producing two concurrent runs and a redundant upload.
- **`uv build --no-sources`** is used, per uv's publishing guide, to verify the package builds with `tool.uv.sources` disabled as other frontends would see it. Currently a no-op, since no `tool.uv.sources` is declared.
- **Tag/version guard.** `GITHUB_REF_NAME` is the tag name for `release` events, so the build job asserts it matches `uv version --short` before building. This catches a mistyped tag before any artifact is produced, which matters because `project.version` is static.
- **`--trusted-publishing always`** fails loudly if the OIDC exchange does not succeed, rather than falling back to an unauthenticated attempt.
- **`setup-uv` in the publish job** uses `enable-cache: false` and `ignore-empty-workdir: true`. There is no checkout, so no lock or manifest exists to key a cache on. No checkout is needed because `uv publish` defaults to the `dist/*` glob; a checkout would only be required for `uv publish --index <name>`, which reads `pyproject.toml`.

### Accepted tradeoff

REPLACING `PYPA/GH-ACTION-PYPI-PUBLISH` WITH `UV PUBLISH` LOSES **AUTOMATIC PEP 740 ATTESTATION GENERATION**. `UV PUBLISH` UPLOADS `*.PUBLISH.ATTESTATION` FILES IT FINDS
ALONGSIDE THE DISTRIBUTIONS (HENCE THE `--NO-ATTESTATIONS` OPT-OUT), BUT PER UV'S OWN
DOCUMENTATION IT "DOES NOT CURRENTLY GENERATE ATTESTATIONS". RESTORING THEM WOULD REQUIRE A
SEPARATE GENERATION STEP. TOOLCHAIN CONSISTENCY WAS JUDGED THE BETTER TRADEOFF FOR A
PURE-PYTHON PACKAGE WITH TRUSTED PUBLISHING ALREADY CONFIGURED.

Several other supposed advantages of the PyPA action do not hold: `uv publish` also retries, re-running the identical command against PyPI is safe because byte-identical files are ignored, and `--check-url` covers the `skip-existing` use case for other registries.

## 6. Version management

`bumpver` was replaced by `uv version`. Removed from `pyproject.toml`: the `[tool.bumpver]` and `[tool.bumpver.file_patterns]` tables, plus the `bumpver` entry in the `dev` group.

Command mapping:

- `bumpver update --patch` &rarr; `uv version --bump patch` (likewise `minor`, `major`)
- preview &rarr; `uv version --bump patch --dry-run`
- read &rarr; `uv version --short`

### Single source of truth for `__version__`

`uv version` only rewrites `project.version` in `pyproject.toml`. Since `dlk/__init__.py` previously carried a duplicated literal maintained by a bumpver file pattern, it now derives the value from installed metadata:

```python
from importlib.metadata import PackageNotFoundError, version

# read the version from the installed package metadata
try:
    __version__ = version("deep-learning-toolkit")
except PackageNotFoundError:
    __version__ = "unknown"
```

Nothing inside `dlk/` or `tests/` consumed `__version__`, so this was a safe change.

### Citation metadata synchronization

`uv version` has no equivalent of bumpver's file patterns, so `CITATION.cff` is synchronized by the `Makefile`:

```make
PY_VERSION       := uv version
CITATION_FILE := CITATION.cff

.PHONY: version version-patch version-minor version-major citation

version:
	@$(PY_VERSION) --short

version-patch:
	$(PY_VERSION) --bump patch
	@$(MAKE) --no-print-directory citation

# sync the version and release date into the citation metadata
citation:
	@version=$$($(PY_VERSION) --short); \
	date=$$(date -u +%F); \
	$(SED) -i "s|^version: .*|version: \"$$version\"|" $(CITATION_FILE); \
	$(SED) -i "s|^date-released: .*|date-released: \"$$date\"|" $(CITATION_FILE); \
	echo "updated $(CITATION_FILE): version $$version, date-released $$date"
```

Two implementation details matter:

- The bump targets reach `citation` through a recursive `$(MAKE)` call. A `$(shell ...)` expansion in the same recipe would evaluate **before** the bump and write the stale version.
- The `version` field in `CITATION.cff` is quoted (`version: "0.4.1"`). The anchored `sed` expression, and previously the bumpver pattern, would otherwise also match `cff-version: 1.2.0`.

This arrangement improves on bumpver in two respects: `date-released` is now updated automatically, and `uv version` locks and syncs by default, so the project version recorded in `uv.lock` stays consistent. Under bumpver that entry went stale on every bump, which would have failed CI via `UV_LOCKED=1` until `uv lock` was run manually.

Not carried over: bumpver's automatic "Bump version X -> Y" commit. Tagging and pushing were already manual (`tag = false`, `push = false`).

## 7. Metadata and licensing

### License change

`GPL-3.0-only` &rarr; `Apache-2.0`. `LICENSE` holds the canonical text from `https://www.apache.org/licenses/LICENSE-2.0.txt` with the appendix placeholder filled in as `Copyright 2024-2026 Johann Rudi` (2024 being the first commit year). No per-file license headers existed anywhere in `dlk/` or `tests/`, so no source changes were needed.

The identifier must be spelled differently in each location: `pyproject.toml`, `.zenodo.json`, `CITATION.cff`: `license = "Apache-2.0"` (SPDX expression).

An invalid value anywhere in `.zenodo.json` aborts the entire Zenodo ingestion, so nothing is archived for that release. The failure surfaces only after a release is cut, which is why the lowercase form matters.

### `.zenodo.json`

The description was expanded from a restatement of the title into a structured abstract covering architectures, training utilities, and supporting components. Zenodo renders it as HTML but sanitizes to a subset — `p`, `a`, `ul`, `ol`, `li`, `strong`, `em`, `br` are safe; `code` is stripped. Ampersands must be escaped as `&amp;`.

`version` is deliberately absent: Zenodo derives it from the release tag, and a hard-coded value would label every release identically.

### `CITATION.cff`

New file, CFF 1.2.0, validated with `uvx cffconvert --validate`. Note that `orcid` must be a full `https://orcid.org/...` URL, unlike the bare identifier used in `.zenodo.json`.

Zenodo **ignores `CITATION.cff` entirely** whenever `.zenodo.json` is present, so the two files can drift silently; title, authors, and license must be kept aligned by hand. The `CITATION.cff` file exists for GitHub's "Cite this repository" UI and for `cffconvert` consumers.

## 8. Documentation updates

`README.md`: removed the non-functional `pip install -e ".[dev]"` and `".[test]"` instructions, added a uv development section (`uv sync`, `uv sync --all-extras`, `uv lock`, and the `UV_LOCKED=1` note), documented `uv build --no-sources`, and added Citing and License sections.

`AGENTS.md`: `Setup` rules rewritten for uv with an explicit rule against `pip install -e ".[dev]"`; new `CI`, `Release`, and `License` sections. The file keeps its rules-only format with no narrative prose.

## 9. Verification performed

- `uv lock --check` &mdash; clean; `bumpver`, `lexid`, and `toml` confirmed absent from the lock.
- `uv build --no-sources` &mdash; sdist and wheel build successfully.
- Wheel metadata inspected: `License-Expression: Apache-2.0`, `License-File: LICENSE`, and the Apache text present at `dist-info/licenses/LICENSE`.
- `uv run python -c "import dlk; print(dlk.__version__)"` &rarr; `0.4.1` from package metadata.
- A real `make version-patch` (0.4.1 &rarr; 0.4.2) confirmed `pyproject.toml`, `uv.lock`, and `CITATION.cff` all update consistently, that `cff-version: 1.2.0` is untouched, and that the result still passes `cffconvert --validate`. Reverted afterwards.
- `uvx cffconvert --validate` &mdash; valid against schema 1.2.0.
- `make format-check` &mdash; clean (37 files in `dlk`, 17 in `tests`).
- `make test` &mdash; 99 passed.

## 10. Open items

- **Attestations are no longer generated** for published distributions (see section 5). Adding a generation step before `uv publish` would restore PEP 740 provenance.
- **Past releases remain GPL-3.0-only.** A license change is not retroactive; the existing PyPI release and Zenodo record keep their original terms. The transition point should be noted in release notes.
- **A `NOTICE` file** is optional under Apache-2.0 but conventional; decide whether to add one, in which case it should also be listed in `license-files`.
