# Implementing Neural Networks Below Python: A Survey for HPC

*Scope: where Python actually costs you in PyTorch, the ladder of lower-level options inside the PyTorch ecosystem, the alternative frameworks worth considering, the complexity each step buys, and a recommendation tailored to a computational-math / scientific-ML group that lives in MFEM / deal.II / PETSc / hypre.*

---

## 1. First, the claim — and why it is only half right

Your implicit hypothesis is: *the Python interface of PyTorch leaves performance on the table.* This is true in a narrow sense and misleading in a broad one, and getting the distinction right determines whether a C++ rewrite is worth your time.

### Where the Python cost lives

There are three distinct Python-attributable costs, and they are often conflated:

1. **Per-operator dispatch overhead.** Every `aten` op (PyTorch has on the order of ~2000 operators counting overloads) passes through the dispatcher, which resolves device/dtype/autograd keys before reaching a kernel. In eager mode each op is dispatched independently. The combined Python-call + dispatch cost is on the order of a few to ~10 microseconds per operator.
2. **The GIL.** Host-side orchestration is single-threaded. You cannot drive several model replicas or several streams from independent Python threads without contention.
3. **Host-side launch latency.** Each CUDA kernel launch is a CPU→GPU submission costing roughly the same order (single-digit µs). This is *not* strictly a Python cost — C++ pays it too — but Python sits on the critical path that feeds it.

### Why these usually don't matter

PyTorch's execution model is **asynchronous**: the host enqueues kernels onto a CUDA stream and runs ahead without waiting for the GPU. To a first approximation, one training iteration costs

$$
T_{\text{iter}} \;\approx\; \max\!\left(\sum_i t^{\text{host}}_i,\;\; \sum_i t^{\text{dev}}_i\right)
$$

— the host pipeline and the device pipeline overlap, so whichever is longer dominates. As long as the GPU has enough work queued that it never stalls waiting for the host, the Python overhead is *hidden behind compute*. For a transformer or CNN at a healthy batch size, $\sum_i t^{\text{dev}}_i$ (big GEMMs, convolutions) dwarfs $\sum_i t^{\text{host}}_i$, and the Python frontend is essentially free. You are GPU-bound, and rewriting the host loop in C++ buys you nothing.

### When the claim becomes true

The overhead *escapes* and becomes the bottleneck precisely when the host pipeline is longer than the device pipeline:

$$
N \cdot \bar t^{\text{host}} \;>\; T_{\text{GPU}}
$$

i.e. **many small kernels** relative to the compute each does. Concretely, you are likely leaving real performance on the table when you have:

- **Small batch sizes or small tensors** — latency-bound inference, single-sample online prediction, small surrogate models.
- **Many tiny ops** — pointwise-heavy graphs, lots of reshapes/indexing, custom physics layers built from dozens of small tensor ops, graph/irregular workloads.
- **CPU-bound surrounding code** — data generation, simulation-in-the-loop, control flow that forces host/device synchronization.
- **Latency-critical deployment** — embedding a surrogate inside a tight solver iteration where each call's wall-clock latency (not throughput) matters.
- **Multi-replica / multi-stream host parallelism** the GIL won't let you express.

This regime is exactly where scientific-ML surrogates often sit: small networks, called millions of times, sometimes inside a C++ solver. So your instinct is sound for *your* domain even though it is wrong for the mainstream large-model training that drives most PyTorch benchmarks.

**Verdict:** the lever is not "Python vs. C++." It is *kernel count and kernel size vs. host overhead*, plus *integration boundary* (does the network need to live inside a C++ process?). Both levers have answers that mostly do **not** require leaving the PyTorch ecosystem — and the ones that do are framework choices, not "drop to C++."

## 2. Diagnose before you port

Before committing to any lower-level path, measure which regime you are in. This is a half-day of work that can save months.

- **`torch.profiler`** with the Chrome/Perfetto trace export. Look at the gaps between kernels on the GPU timeline. Solid wall of kernels = GPU-bound (Python is free; stop here). Gaps with the CPU racing ahead and the GPU idle = host/launch-bound (the regime where lower-level work pays).
- **The synchronization test.** Time the loop normally, then time it with `torch.cuda.synchronize()` removed/added and a fixed kernel count. If forcing periodic syncs barely changes throughput you are device-bound.
- **The "Nsight Systems" view** (`nsys`) gives you the host-launch vs. device-execution overlap explicitly, including NCCL.
- **Count your ops.** A forward pass dominated by a handful of large GEMMs is a different animal from one with 400 small elementwise kernels.

Only after this should you pick a rung on the ladder below.

## 3. The ladder inside PyTorch (lowest friction first)

You can recover almost all of the "Python tax" without abandoning the ecosystem you already know. These are ordered by increasing effort and increasing distance from Python.

### Rung 0 — `torch.compile` + CUDA graphs (stay in Python)

This is the highest-leverage, lowest-cost move and it directly attacks the overhead you are worried about.

- **`torch.compile`** captures the graph via TorchDynamo, traces forward+backward via AOTAutograd, lowers through PrimTorch/Inductor, and **fuses** ops into a smaller number of Triton (GPU) or C++/OpenMP (CPU) kernels. Fusion reduces both kernel count and memory traffic.
- **`mode="reduce-overhead"`** additionally wraps execution in **CUDA graphs**: a captured sequence of kernel launches is replayed as a *single* host submission, eliminating per-kernel launch overhead. This is the mechanism that removes the regime in §1. For static shapes it can collapse the entire host pipeline to one launch.

A widely reported and important nuance: for many models, **most of the `torch.compile` speedup actually comes from the CUDA-graph capture, not from operator fusion** — fusion and autotuning add substantial compile time for marginal steady-state gains. You can even use `torch.cuda.graph` / `torch.cuda.make_graphed_callables` directly without `torch.compile` if launch overhead is your only problem. Caveats: CUDA graphs require **static shapes and stable tensor addresses** (re-recording per shape; the caching allocator pins memory), and they exclude data-dependent control flow. For fixed-size scientific surrogates this constraint is usually a non-issue.

> If your profiling in §2 says "host/launch-bound," try this *first*. It frequently closes the gap entirely, in pure Python.

### Rung 1 — custom kernels (the real FLOPs lever)

If you are GPU-bound, the only way to go faster is to make the kernels themselves better — and this is where genuine HPC performance lives, far more than at the language boundary.

- **Triton** (`@triton.jit`) — Python-syntax kernel language that compiles to fast GPU code; the same backend Inductor emits. Lets you write fused, hardware-aware kernels (custom attention, fused physics operators) without CUDA C++. Excellent effort/return ratio.
- **CUDA C++ extensions** via `torch.utils.cpp_extension` (`load`/`load_inline` for JIT, or a `setup.py` build). You write `__global__` kernels and bind them as ops. Full control; full CUDA toolchain responsibility.
- **Custom ops** via `torch.library` / the `TORCH_LIBRARY` API — register your kernel as a first-class `aten`-style op with an autograd formula, so it composes with autograd, `torch.compile`, and the dispatcher. This is the *right* way to integrate a hand-written kernel.

This rung is orthogonal to the Python question: you keep the Python frontend and only replace the hot kernels. For most "I need more performance on this specific operator" problems, this is the answer.

### Rung 2 — LibTorch (the C++ frontend)

LibTorch is PyTorch's **C++ API** over the same ATen tensor library and the same C++ autograd engine. `torch::nn`, `torch::optim`, and autograd all exist in C++ with deliberately PyTorch-like signatures. You can write the **entire training loop** — model, loss, optimizer, backward — in C++ with no Python interpreter present.

What this actually buys you:

- **No GIL, no Python interpreter** on the host path → you can multi-thread orchestration, run many replicas, drive multiple streams.
- **Native embedding** into an existing C++ application — the decisive feature for your stack. A LibTorch surrogate links directly into a PETSc/MFEM/deal.II driver and is called in-process with no IPC.
- Deterministic memory and stream control.

What it does **not** buy you: the kernels are *identical* to Python PyTorch's, so a clean GPU-bound training loop will run at the same speed. The win is overhead elimination and integration, not faster math. You also inherit a real build-system and ABI burden (see §5).

### Rung 3 — `torch.export` + AOTInductor (compile to a standalone `.so`)

This is the most important recent development for your use case and it deserves emphasis. The workflow:

1. `torch.export.export(model, example_inputs, dynamic_shapes=...)` captures a sound, specified graph (handles dynamic dims via `torch.export.Dim`).
2. `torch._inductor.aoti_compile_and_package(...)` runs **AOTInductor** (an ahead-of-time TorchInductor) to produce a **self-contained shared library / `.pt2` package** containing precompiled Triton kernels as cubins.
3. The artifact is loaded and invoked from **C++** (`torch._inductor.aoti_load_package`, or the C++ runtime), with no Python and — unlike JIT `torch.compile` — **no first-call warmup cost** at deployment time.

Why this matters for you: you can develop and train the surrogate in comfortable Python PyTorch, then ship a dependency-light compiled artifact that a C++ HPC code links against for inference. It is the cleanest "train in Python, predict in C++" path. (Limitations: AOTInductor packaging is currently Linux-only; no built-in CUDA-graph wrapping, though you can orchestrate graphs around it; primarily an inference-deployment path, though export of training graphs is advancing.)

### Rung 4 — ExecuTorch (edge / embedded)

`torch.export` → EXIR → flatbuffer → a tiny C++ runtime. Optimized for minimal binary size and startup, for phones/wearables/microcontrollers. Relevant if you ever target embedded inference (e.g. the Jetson-class on-prem hardware), much less so for cluster work. Mentioned for completeness.

## 4. Leaving PyTorch: the alternatives

If the diagnosis points to something structural — you want whole-program compilation, a different autodiff model, a GIL-free typed language end to end, or tighter HPC integration — these are the serious options.

### JAX / XLA — the strongest fit for differentiable scientific computing

JAX is *not* "C++ instead of Python." Its frontend is Python; the point is that `jax.jit` traces your function and hands a whole program to the **XLA** compiler, which does fusion, layout, and scheduling across the entire computation — so the per-op Python overhead simply does not exist after the first trace. It compiles a *function*, not just a model.

Why it is compelling specifically for your work:

- **Composable function transforms:** `grad`/`jacfwd`/`jacrev`/`hessian` (forward and reverse mode, higher-order), `vmap` (auto-batching), `pmap`/`shard_map`/`jit` with sharding (multi-device). For **PINNs and physics-informed regularization** you need derivatives of the network *with respect to inputs* and higher-order derivatives — JAX expresses this far more naturally than PyTorch.
- **`vmap` for amortized inference and ensembles:** your "amortized inference" and "Bayesian inversion with NN surrogates" goals map almost directly onto vectorized, vmapped evaluations — exactly JAX's sweet spot.
- **Functional purity** matches how numerical methods are usually specified, and the SciML ecosystem (Diffrax for ODEs/SDEs, Equinox for models, Optax for optimizers, BlackJAX for MCMC, Lineax/jaxopt for solvers) is mature and aimed at people like you.

Trade-offs: the functional/immutable style and `jit`'s static-shape/`tracer` constraints have a learning curve; compilation overhead can be large for dynamic control flow; the deployment-to-C++ story is weaker than PyTorch's AOTInductor (you generally keep Python at the boundary or go through XLA AOT / IREE). For training differentiable-physics surrogates, JAX is often the better tool; for *embedding the trained surrogate in a C++ solver*, PyTorch's export path is currently smoother.

### The Rust frameworks

A genuinely different answer to "remove Python without writing CUDA C++ by hand": a statically typed, GIL-free, memory-safe language with a real package manager, end to end.

| Framework | What it is | Training | Backends | Best for |
|---|---|---|---|---|
| **tch-rs** | Rust bindings to LibTorch | Yes (via LibTorch) | Whatever LibTorch supports | Reusing the PyTorch ecosystem from Rust; experimentation; depends on libtorch |
| **candle** (HuggingFace) | Minimalist tensor lib | Basic (autodiff, optimizers) | CPU, CUDA, Metal | Lightweight, fast, low-footprint *inference*; serverless; removing Python+GIL from production |
| **burn** (tracel-ai) | Full DL framework | Yes, first-class | Pluggable via **CubeCL** (CUDA, ROCm, WGPU, NdArray, plus a LibTorch/candle backend) | Full train→deploy lifecycle in Rust with hardware portability and static-graph-style optimizations without losing flexibility |

candle's stated rationale is exactly your hypothesis stated baldly: Python overhead can hurt and the GIL is a recurring source of pain, so they remove Python from production. burn is the most ambitious — it gets static-graph optimizations through Rust's type system while keeping a customizable training loop, and its CubeCL layer lets you write kernels once and target multiple GPUs. The cost is a smaller ecosystem and the need to be (or grow) a Rust shop — a real consideration for a rotating cast of graduate students.

### Minimal / from-scratch stacks

- **tinygrad** — deliberately tiny, lazy-evaluated, with a small set of ops lowered to custom backends. Excellent for *understanding* the whole stack and for hackable backends; not where you'd run production HPC, but pedagogically and architecturally illuminating (and aligned with your interest in network internals).
- **ggml / llama.cpp** — hand-written C/C++ tensor + inference engine, no autodiff to speak of. The right reference if you want to see "inference with zero framework," but you'd be reimplementing a lot.

### Bare metal and compiler infrastructure

At the bottom you can call the vendor libraries directly — **cuBLAS, cuDNN, CUTLASS** (templated GEMM/conv building blocks), Thrust/CUB — and assemble your own training loop. You would own autograd entirely (a tape, or hand-coded adjoints). This is rarely worth it for whole networks, but it is exactly the toolkit for one custom fused kernel that you then expose back to PyTorch via Rung 1.

For a research group that already thinks in performance-portability terms, two adjacent ecosystems are worth knowing: **Kokkos** (performance-portable C++ parallelism, the lingua franca of much of DOE HPC) for hand-rolled kernels, and the **MLIR / OpenXLA / IREE** compiler stack, which is where the whole field's lowering infrastructure is converging (XLA, Triton, and Torch-MLIR all touch it). If your "agentic AI for scientific computing" and DOE-adjacent work pulls you toward custom compilation, MLIR is the substrate.

## 5. The complexity tax — what each step down actually costs

Every rung below pure-Python PyTorch trades iteration speed and ecosystem for control. Be explicit about the bill:

**Autograd is the big one.** In Python you take backward passes for granted. LibTorch and burn and JAX give you autograd; candle's is basic; ggml and bare-CUDA give you *nothing* and you implement adjoints by hand. For scientific ML this is double-edged: you often *want* explicit adjoints (for PDE-constrained optimization, the discrete adjoint is a known quantity), but reimplementing and *verifying* gradients (finite-difference checks, gradient tests) is real, error-prone work.

**Build systems, ABI, and packaging.** LibTorch means CMake, matching the C++ ABI (`cxx11` vs pre-cxx11), matching CUDA/cuDNN versions exactly to the libtorch build, and shipping large shared libraries. CUDA C++ extensions add nvcc, architecture flags (`sm_90` etc.), and a compile step to every change. This is the friction that turns a 30-second Python edit-run cycle into minutes.

**Ecosystem loss.** You give up, and must re-source or rebuild: data loaders and augmentation, the optimizer/scheduler zoo, mixed precision (`autocast`/`GradScaler`), distributed training (DDP/FSDP/NCCL glue), checkpointing, experiment tracking, and — not least — the *debugging and profiling* tooling. A Python stack trace and `pdb` become a C++ core dump and `gdb`/`cuda-gdb`.

**Iteration speed collapse.** The deepest hidden cost. Research throughput is bounded by how fast you can try ideas. Dropping to C++ for a not-actually-bottlenecked loop can slow your *science* even as it speeds your *kernels*.

**Multi-hardware maintenance.** Hand-written CUDA is NVIDIA-only unless you also do ROCm/SYCL. Triton, burn/CubeCL, and XLA buy back some portability; raw kernels do not.

**People.** For a lab with rotating students, every step down raises the onboarding bar. LibTorch-literate or Rust-literate students are scarcer than PyTorch-literate ones. This is a staffing decision as much as a technical one.

A useful heuristic: **the cost of a rung is roughly proportional to how much of autograd + ecosystem + build you take on yourself, and the benefit is proportional to how host-bound or integration-bound you actually are.** Match the two using §2.

## 6. Recommendation for your context

Given the profile — computational math, scientific ML, MFEM / deal.II / PETSc / hypre, Bayesian inversion with NN surrogates, PINNs, amortized inference, on-prem hardware — the highest-value moves are *integration* and *autodiff fit*, not a wholesale C++ rewrite of training.

**1. If the goal is "run a trained surrogate inside a C++ PDE solver":** this is your most likely real need, and it has a clean answer. Train in Python PyTorch, then export via **`torch.export` + AOTInductor** to a standalone `.so`/`.pt2` and link it into your PETSc/MFEM/deal.II driver. No Python at runtime, no warmup, minimal dependencies. Use **LibTorch** instead only if you need to *train or fine-tune inside* the C++ process, or to differentiate *through* the surrogate within the solver (e.g. coupling adjoints).

**2. If the goal is differentiable physics / PINNs / amortized inference:** seriously evaluate **JAX**. `grad`/`hessian` composability handles physics-informed derivative terms cleanly, `vmap` is tailor-made for amortized/ensemble inference and your sparse-grid surrogate sweeps, and the SciML libraries (Diffrax, Equinox, Optax, BlackJAX) are built for inverse problems. The functional rewrite is the cost; the autodiff and batching ergonomics are the payoff.

**3. If the goal is raw throughput on a specific operator:** stay in Python and go to **Rung 0 then Rung 1** — `torch.compile`/CUDA graphs first, then a **Triton** or CUDA custom op registered via `torch.library`. This is where actual FLOPs gains live, and it costs you almost no ecosystem.

**4. Treat a full C++/Rust training rewrite as a last resort,** justified only if profiling shows a persistent host-bound loop that CUDA graphs cannot fix, *or* a hard requirement for GIL-free multi-replica orchestration, *or* a deployment target with no Python. If you do go typed-language, **burn** (full lifecycle, portable) or **tch-rs** (reuse PyTorch) are the pragmatic choices; **candle** if it is inference-only.

### Decision sketch

```
Profile (§2)
├─ GPU-bound? ──────────────► kernels are the only lever
│                              └─ Rung 1: Triton / CUDA custom op (stay in Python)
│
├─ Host/launch-bound? ──────► Rung 0: torch.compile(mode="reduce-overhead")
│                              └─ still bound & static shapes? raw CUDA graphs
│                              └─ GIL-blocked multi-replica? ──► LibTorch / Rust
│
└─ Integration-bound? (must live in C++)
   ├─ inference only ───────► torch.export + AOTInductor  (.so into PETSc/MFEM)
   ├─ train/adjoint in-proc ► LibTorch
   └─ differentiable physics► JAX (then deploy via XLA AOT / keep Py boundary)
```

### Testing your original hypothesis empirically

To actually measure "what Python costs me" on a representative surrogate:

1. Build the network and a fixed-shape forward+backward in eager PyTorch; time it with `torch.profiler` and record GPU-idle gaps.
2. Wrap it in `torch.compile(mode="reduce-overhead")`; re-time. The delta is the recoverable host/launch overhead — *available without leaving Python*.
3. Port the same loop to **LibTorch**; re-time. Any delta *beyond* step 2 is the residual interpreter/GIL cost — usually small for a clean loop, meaningful only if you saturate the host or need threads.
4. If step 3's delta is negligible (the common outcome for GPU-bound work), your performance lever is kernels (Rung 1) or integration (export/LibTorch), and the language was never the bottleneck.

That four-step experiment will tell you, for your models, exactly how much is on the table and where — which is a far firmer footing than the untested intuition you started with.
