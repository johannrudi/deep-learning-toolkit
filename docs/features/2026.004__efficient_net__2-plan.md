## 1. Context

`dlk/nets/efficientnet1d.py` already has `MBConv1D` and `FusedMBConv1D`, the 1D adaptations of the two block types EfficientNet V1 and V2 are built from, plus a toy `EfficientNet1D` model whose stage widths (16/8/12/20/40/56/96/160) are a hand-tuned, much smaller stand-in for the real B0 and do not match either published architecture. This plan adds two new model classes that reproduce the real EfficientNetV1-B0 and EfficientNetV2-S macro-architectures, stage-for-stage, using the two existing block classes.

The reference is the original Google implementation, <https://github.com/google/automl/>: `effnetv2_configs.py` (`v1_b0_block_str`, `v2_s_block`, `efficientnetv1_params`, `efficientnetv2_params`) for the per-stage tables and `effnetv2_model.py` (`round_filters`, `round_repeats`, `MBConvBlock`, `FusedMBConvBlock`, `Stem`, `Head`, `EffNetV2Model._build`) for how those tables become a network.

Both target configurations use `width_coefficient = depth_coefficient = 1.0`, so no channel or repeat count actually changes under scaling for **B0 or V2-S**; the plan still implements the general `round_filters`/`round_repeats` scaling functions because build was explicitly scoped as reusable infrastructure for future variants (B1-B7, V2-M/L/XL), not just a one-off.

### 1.1 Correctness finding: squeeze-and-excitation bottleneck sizing

Cross-checking `MBConv1D` against upstream's `MBConvBlock._build` (`effnetv2_model.py:240-243`) surfaced a real discrepancy, not just a style difference. Upstream sizes the SE bottleneck from the block's pre-expansion input channels: `num_reduced_filters = max(1, int(input_filters * se_ratio))`, then gates the post-expansion tensor (`filters = input_filters * expand_ratio` channels) through that bottleneck.

`MBConv1D` (`dlk/nets/efficientnet1d.py:210-216`) instead calls `SqueezeExcitation1D(expanded_channels, config.se_ratio)`, and `SqueezeExcitation1D.__init__` (`dlk/nets/efficientnet1d.py:132-149`) computes `squeeze_channels = int(input_channels * se_ratio)` from whatever channel count it is given, i.e. from `expanded_channels`, not the true pre-expansion `input_channels`. For `expand_ratio == 1` stages the two formulas agree; every `expand_ratio in {4, 6}` stage in B0 and V2-S (the majority of blocks in both models) gets an SE bottleneck up to 6x wider than upstream, which changes parameter count and the strength of the channel gating.

**Reproducing "the real B0" and "the real V2-S" requires fixing this**, so the fix is included as a required correctness change, called out separately from the new, purely additive code in section 3 below.

### 1.2 Settled design decisions

- One general, compound-scalable model class implements both families' shared topology (stem, a sequence of per-stage blocks, head), parameterized by a list of per-stage block specs plus `width_coefficient`/`depth_coefficient`; this mirrors upstream's own `EffNetV2Model`, which is a single class for both V1 and V2, selecting `MBConvBlock` vs. `FusedMBConvBlock` per stage via a `conv_type` flag.
- `EfficientNet1D` and `get_efficientnet_b0_config` stay exactly as they are; the new models are additive, not a replacement, to avoid disturbing any existing caller.
- The new public entry points are named `EfficientNetV1B0` and `EfficientNetV2S` (no redundant `1D` suffix), backed by config builders `get_efficientnet_v1_b0_config` and `get_efficientnetv2_s_config`.

### 1.3 Core principle

Network topology is generic and data-driven: the stem/blocks/head wiring is written once, and everything that differs between EfficientNet variants, kernel sizes, strides, expansion ratios, channel counts, repeat counts, SE ratios, and which block class implements each stage, lives in a per-stage config list. Adding a future variant (B1-B7, V2-M/L/XL) is then a new config-builder function plus a thin subclass fixing its coefficients and stem/head widths; the shared builder logic needs no changes.

## 2. Terminology

- **Stage**: a group of one or more blocks that share a kernel size, expansion ratio, and channel counts; only the first block in a stage applies the stage's stride, later blocks in the same stage run at stride 1 on the stage's output channels.
- **Compound scaling**: EfficientNet's rule for deriving a larger model from a base config by multiplying every stage's channel count by a `width_coefficient` and every stage's repeat count by a `depth_coefficient`, then rounding channels to a multiple of a divisor (`round_filters`) and repeats up to the nearest integer (`round_repeats`).
- **Fused-MBConv**: the V2 block that merges the expansion and spatial-filter steps into one dense convolution (`FusedMBConv1D`); it never has squeeze-and-excitation in either target config.
- **MBConv**: the V1/V2 block with a separate pointwise expansion, a depthwise spatial filter, and optional squeeze-and-excitation (`MBConv1D`).
- **Squeeze-and-excitation (SE) bottleneck**: the reduced channel width inside the SE gate; upstream derives it from the block's pre-expansion input channels, not its expanded channels (section 1.1).
- **Survival probability**: the residual-branch keep-probability upstream schedules linearly per block index; the existing blocks approximate this with plain per-element `nn.Dropout` on the pre-residual tensor rather than upstream's per-sample stochastic depth, an existing simplification this plan does not change (see section 7).

## 3. `dlk/nets/efficientnet1d.py`: correctness fix for SE bottleneck sizing

Pre-change lines: `SqueezeExcitation1D.__init__` at `dlk/nets/efficientnet1d.py:132-149`, its call site in `MBConv1D.__init__` at `dlk/nets/efficientnet1d.py:210-216`.

Change `SqueezeExcitation1D.__init__` to take the bottleneck width as an explicit argument instead of computing it from `se_ratio` internally: `def __init__(self, channels: int, squeeze_channels: int) -> None`, keeping the same `nn.AdaptiveAvgPool1d` -> `Conv1d` -> `Swish` -> `Conv1d` -> `Sigmoid` body but building the two `Conv1d` layers from `channels`/`squeeze_channels` directly.

In `MBConv1D.__init__`, compute `squeeze_channels = max(1, int(config.input_channels * config.se_ratio))` (pre-expansion channels, matching upstream) and construct `self.se = SqueezeExcitation1D(expanded_channels, squeeze_channels)`.

This only changes internal wiring; `MBConv1D`'s public forward behavior (shapes, residual logic) is unchanged, so the existing `MBConv1D` shape tests in `tests/nets/test_efficientnet1d.py` keep passing unmodified.

## 4. `dlk/nets/efficientnet1d.py`: compound-scaling helpers and `StageSpec`

Add near `MBConvConfig` (after `dlk/nets/efficientnet1d.py:34`), in the `# Config` section: a module-level `import math` at the top of the file, a `round_filters(filters: int, width_coefficient: float, depth_divisor: int = 8, min_depth: int | None = None) -> int` function, and a `round_repeats(repeats: int, depth_coefficient: float) -> int` function, both direct ports of `effnetv2_model.py:84-102` (no 0.9-safeguard branch; upstream does not have one).

Add a `StageSpec(NamedTuple)` with fields `block_cls: type[nn.Module]` and `config: MBConvConfig`, pairing a stage's config with the block class (`MBConv1D` or `FusedMBConv1D`) that should implement it; this keeps `MBConvConfig` free of a block-type field and needs no change to `get_efficientnet_b0_config` or its existing config values.

## 5. `dlk/nets/efficientnet1d.py`: canonical stage configs for V1-B0 and V2-S

Add these after `FusedMBConv1D` (after `dlk/nets/efficientnet1d.py:375`), since they build `StageSpec` values that reference `MBConv1D`/`FusedMBConv1D` by name. `get_efficientnet_v1_b0_config() -> list[StageSpec]` returns the decoded form of `v1_b0_block_str` (`effnetv2_configs.py:93-101`), all stages using `MBConv1D`:

- k3 s1 e1 i32 o16 r1 se0.25
- k3 s2 e6 i16 o24 r2 se0.25
- k5 s2 e6 i24 o40 r2 se0.25
- k3 s2 e6 i40 o80 r3 se0.25
- k5 s1 e6 i80 o112 r3 se0.25
- k5 s2 e6 i112 o192 r4 se0.25
- k3 s1 e6 i192 o320 r1 se0.25

`get_efficientnetv2_s_config() -> list[StageSpec]` returns the decoded form of `v2_s_block` (`effnetv2_configs.py:150-157`), stages 1-3 using `FusedMBConv1D` with `se_ratio=None`, stages 4-6 using `MBConv1D` with `se_ratio=0.25`:

- FusedMBConv1D: k3 s1 e1 i24 o24 r2
- FusedMBConv1D: k3 s2 e4 i24 o48 r4
- FusedMBConv1D: k3 s2 e4 i48 o64 r4
- MBConv1D: k3 s2 e4 i64 o128 r6 se0.25
- MBConv1D: k3 s1 e6 i128 o160 r9 se0.25
- MBConv1D: k3 s2 e6 i160 o256 r15 se0.25

Both add up to the published block counts: 16 blocks for B0 (1+2+2+3+3+4+1), 40 blocks for V2-S (2+4+4+6+9+15), and both have a total stride of 32 (stem stride 2, plus four stride-2 stages), matching the published stride for both families.
Section 14 catalogs every other published V1 and V2 variant (B1-B8, L2 for V1; B0-B3, M, L, XL for V2) in the same notation, for later config builders; this plan's initial scope only implements the two configs above.

## 6. `dlk/nets/efficientnet1d.py`: `ScalableEfficientNet1D`, `EfficientNetV1B0`, `EfficientNetV2S`

Add after `EfficientNet1D` (after `dlk/nets/efficientnet1d.py:508`), in the `# EfficientNet` section.

`ScalableEfficientNet1D(nn.Module)` takes `stage_specs: list[StageSpec]`, `stem_channels: int`, `head_channels: int = 1280`, `width_coefficient: float = 1.0`, `depth_coefficient: float = 1.0`, `depth_divisor: int = 8`, `min_depth: int | None = None`, plus the same runtime knobs `EfficientNet1D` already exposes (`input_channels`, `input_length`, `num_classes`, `dropout_connect`, `dropout_head`).

Its `__init__` rescales every stage spec's config with `round_filters`/`round_repeats`, builds the stem from `round_filters(stem_channels, ...)`, builds `self.blocks` with the same per-stage loop pattern as `EfficientNet1D.__init__` (`dlk/nets/efficientnet1d.py:424-438`) except it instantiates `spec.block_cls(block_config, dropout_block)` instead of hardcoding `MBConv1D`, and builds the head from `round_filters(head_channels, ...)`.

`forward` and `_initialize_weights` mirror `EfficientNet1D`'s (`dlk/nets/efficientnet1d.py:348-360, 362-400`) exactly; per the settled decision to leave `EfficientNet1D` untouched, this is accepted small duplication rather than an extraction that would touch the existing class.

`EfficientNetV1B0(ScalableEfficientNet1D)` and `EfficientNetV2S(ScalableEfficientNet1D)` each expose only the runtime knobs (`input_channels`, `input_length`, `num_classes`, `dropout_connect`, `dropout_head`) and call `super().__init__` with their fixed `stage_specs`, `stem_channels` (32 for B0, 24 for V2-S), `head_channels=1280`, and `width_coefficient=depth_coefficient=1.0`; `dropout_head` defaults to `0.2` for both, matching `efficientnetv1_params['efficientnet-b0']` and `efficientnetv2_params['efficientnetv2-s']`.

## 7. Usage sketch

There is no existing caller to migrate; both classes are new, additive public symbols with the same call signature shape as `EfficientNet1D`:

```python
from dlk.nets.efficientnet1d import EfficientNetV1B0, EfficientNetV2S

model_b0 = EfficientNetV1B0(input_channels=1, input_length=1024, num_classes=5)
model_v2s = EfficientNetV2S(input_channels=1, input_length=1024, num_classes=5)

logits = model_b0(x)  # x: (batch_size, 1024) or (batch_size, 1, 1024)
```

## 8. Tests

Add to `tests/nets/test_efficientnet1d.py`, following its existing style:

- `test_round_filters_rescales_channels_at_a_nontrivial_coefficient`: check `round_filters(40, 1.1) == 48` (rounds up) and `round_filters(32, 1.1) == 32` (rounds back down to the same value), using `efficientnet-b2`'s published `width_coefficient=1.1` as the input so the expected values are independently checkable against `effnetv2_configs.py:108`.
- `test_round_repeats_rounds_up_fractional_depth`: check `round_repeats(2, 1.2) == 3` and `round_repeats(1, 1.2) == 2`, using B2's `depth_coefficient=1.2`.
- `test_squeeze_excitation1d_bottleneck_matches_explicit_channels`: build `SqueezeExcitation1D(channels=24, squeeze_channels=6)` directly and check the first and last `Conv1d` layers' `in_channels`/`out_channels`, pinning the new explicit-width constructor contract from section 3.
- `test_mbconv1d_se_bottleneck_uses_pre_expansion_channels`: build an `MBConv1D` with `expand_ratio=6`, `input_channels=16`, `se_ratio=0.25`, and check `block.se.se[1].out_channels == 4` (`int(16 * 0.25)`), not `int(96 * 0.25) == 24`; this is the ship gate for the section 3 correctness fix, since a regression here silently reintroduces the wrong SE width.
- `test_efficientnet_v1_b0_forward_output_shape`: run `EfficientNetV1B0(input_length=320, num_classes=3)` on `torch.randn(2, 320)` and check the output shape is `(2, 3)`.
- `test_efficientnet_v1_b0_has_expected_block_count`: check `len(model.blocks) == 16`.
- `test_efficientnet_v2_s_forward_output_shape`: run `EfficientNetV2S(input_length=320, num_classes=3)` on `torch.randn(2, 320)` and check the output shape is `(2, 3)`.
- `test_efficientnet_v2_s_has_expected_block_count`: check `len(model.blocks) == 40`.
- `test_efficientnet_v2_s_uses_fused_blocks_in_early_stages_and_mbconv_in_late_stages`: check `isinstance(model.blocks[0], FusedMBConv1D)`, `isinstance(model.blocks[9], FusedMBConv1D)` (last of the three fused stages, index 2+4+4-1), and `isinstance(model.blocks[10], MBConv1D)` (first MBConv stage block), plus `model.blocks[10].has_se is True` and `model.blocks[0].config.se_ratio is None`.

## 9. Documentation

This plan is the primary documentation artifact; no separate usage guide is warranted yet since the two classes follow the same call pattern as the already-documented `EfficientNet1D`.

## 10. Unrelated improvements observed

- The residual-branch dropout in both blocks is per-element `nn.Dropout`, not upstream's per-sample stochastic depth (drops the entire residual branch for some samples in a batch, scaling the rest); the drop-rate schedule matches upstream's numerically, but the mechanism differs, out of scope here.
- `get_efficientnet_b0_config`'s name is easy to confuse with the new, faithful `get_efficientnet_v1_b0_config`; the settled decision (section 1.2) is to leave it as-is, but a follow-up rename or docstring clarification would reduce that risk.

## 13. Risks / edge cases

- `FusedMBConv1D` stage 1 of V2-S has `expand_ratio=1`, so every block in it collapses to a single dense conv with no separate projection (`dlk/nets/efficientnet1d.py:321-335`); both its blocks have matching input/output channels (24) and stride 1, so both take the residual path, this is the intended upstream behavior, not a bug.
- Channel counts are carried over unchanged from the original 2D image models; they were tuned for RGB image classification, not 1D signals, so they may be oversized or undersized for a given signal task, this plan only asks for architectural fidelity, not task-specific retuning.
- `round_filters`/`round_repeats` are unused with any coefficient other than 1.0 until a future variant is added; the two new tests in section 8 are the only coverage for their scaling behavior until then.

## 15. Appendix: minimal EfficientNets

Both minimal configs reuse the existing compound-scaling infrastructure (`round_filters`/`round_repeats`, section 4) with `width_coefficient` and `depth_coefficient` below `1.0`, applied to the unscaled `get_efficientnet_v1_b0_config` and `get_efficientnet_v2_b_config` base tables (sections 5 and 14.2); no new mechanism is needed, only new coefficients and two thin `ScalableEfficientNet1D` subclasses analogous to the B1-B8/M/L/XL pattern.

A grid search over `width_coefficient` in `[0.10, 0.50]` and `depth_coefficient` in `[0.50, 1.00]` (stem/head base channels left at `32`/`1280`, `depth_divisor=8`, `min_depth=8`) showed the channel floor (`min_depth=8`) dominates below `width_coefficient≈0.15`: at `width=0.10, depth=1.0` almost every stage collapses to the `8`-channel floor and only the last one or two stages differ, which keeps the full block count but loses the widening channel progression that identifies the family. `width_coefficient=0.15, depth_coefficient=0.5` keeps a visible per-stage channel progression (`8 -> 8 -> 8 -> 16 -> 16 -> 32 -> ...`) while still landing well under the `100,000`-parameter budget, so both minimal configs below use that pair. Parameter counts were verified by instantiating the model with `input_channels=1`, `num_classes=2`, `input_length=None` and summing `p.numel()` over parameters with `requires_grad`; the head and final linear layer only add a few hundred parameters per extra class, so the totals below are not sensitive to `num_classes`.
