# Composing existing networks into a directed acyclic graph

## 1. Context

`dlk/nets/` offers seven network families that each solve one topology end to end:

- `MLPNet`, `MLPNet_MultIn`, `MLPResNet` (`dlk/nets/mlp.py`),
- `ConvNet`, `ConvResNet` (`dlk/nets/conv1d.py`),
- `TransformerNet`, `ChannelWiseTransformerNet` (`dlk/nets/transformer1d.py`), and the
- EfficientNet family (`dlk/nets/efficientnet1d.py`).

There is no way to build a network out of two or more of them. An application that wants a convolutional stem over a time series, a separate stem over a latent vector, and a residual trunk over both stems' outputs has to write a bespoke `nn.Module` and recompute every concatenation width by hand.

The motivating case is a conditional generator whose feature stem is an `EfficientNetV1B0Minimal` with a configurable output size, whose latent stem is an `MLPResNet`, and whose trunk is an `MLPResNet` over the two stems' concatenated outputs. Nothing about that shape is specific to one application, so the composition belongs in `dlk`.

This plan adds `dlk/nets/compose.py`: a `ComposedNet` that wires already-built `dlk` networks into a directed acyclic graph, a shape protocol so edge widths are derived rather than typed in, typed config dataclasses describing the graph, and a graph-aware partial forward that makes latent-replica `vmap` work with stems that carry batch normalization.

### 1.1 Current state and gaps found while exploring

`ScalableEfficientNet1D` is already half-prepared for this. Commit `6372185` added `enable_stem` and `enable_head` (`dlk/nets/efficientnet1d.py:404-419`) together with `resolve_input_channels()` and `resolve_output_size()` (`dlk/nets/efficientnet1d.py:573-593`), explicitly "for composition purposes". A stem with `enable_head=True` and `num_classes` set to the wanted width is exactly the configurable-output-size stem this plan needs, and `resolve_output_size()` already reports that width.

Four gaps stand out, and each becomes a plan item.

1. **The shape accessors are an EfficientNet-only convention.** `MLPNet` stores `input_size` (`dlk/nets/mlp.py:57`) and nothing about its output; `MLPResNet` stores the resolved `input_size` (`dlk/nets/mlp.py:617-624`) but not `output_size`, although its own `ResidualBlock` stores both (`dlk/nets/mlp.py:461-462`); `ConvNet` and `ConvResNet` store `input_channels` only (`dlk/nets/conv1d.py:73`, `dlk/nets/conv1d.py:187`); `TransformerNet` and `ChannelWiseTransformerNet` store `input_seq_size` and keep the output width inside `self.head` (`dlk/nets/transformer1d.py:447`, `dlk/nets/transformer1d.py:463`, `dlk/nets/transformer1d.py:546-567`). Composition needs two uniform questions it can ask any node, what it takes and what it returns, so the convention gets generalized into a protocol and the missing accessors get written.
2. **`enable_stem`, `enable_head`, `resolve_input_channels` and `resolve_output_size` have no tests.** `tests/nets/test_efficientnet1d.py` exercises block counts, forward shapes and scaling helpers, and never touches the four composition hooks. The first consumer of those hooks should not also be their first test, and the two accessors are being replaced by the protocol pair (section 10), which is a rename no test currently guards.
3. **The pooling sits inside the head, not before it.** `ScalableEfficientNet1D`'s head is `Conv1d -> BatchNorm1d -> SiLU -> AdaptiveAvgPool1d(1) -> Flatten -> Dropout -> Linear` (`dlk/nets/efficientnet1d.py:526-543`), so `enable_head=False` replaces the pooling along with the classifier and `forward` returns an unpooled feature map of shape `(batch, channels, length')` (`dlk/nets/efficientnet1d.py:595-635`). A headless stem therefore is not effectively one-dimensional. Nothing computes `length'` either, so a headless stem can report its output shape only as `(channels, None)` without replicating the stride arithmetic. This is the reason feature-map edges are out of scope here (section 1.2).
4. **`dlk/opt/train_gan.py` fixes the call contract.** It calls `g_net(y_data, z)` and `d_net(x_gen, y_data)` positionally (`dlk/opt/train_gan.py:384-387`, `dlk/opt/train_gan.py:477-480`). A composed net has to be a drop-in at those two call sites, which means its external inputs need a declared positional order.

The replica question is the sharp edge. An application that draws several latent samples per observation evaluates the generator once per replica, typically with `torch.vmap` over the latent dimension. `MLPResNet` and `ConvResNet` tolerate that because their normalization is `nn.LayerNorm` (`dlk/nets/mlp.py:471`), which holds no running state. Every EfficientNet block carries `nn.BatchNorm1d`, whose running-statistics update is an in-place write into an unbatched buffer and raises under `vmap` in training mode. The feature stem does not depend on the latent at all, so evaluating it inside the vmapped region is both incorrect and wasteful: at 100 replicas it recomputes the same stem output 100 times. Splitting the graph at the dependency boundary fixes both, and reachability is a property of the graph, so `dlk` is where it can be computed and tested.

### 1.2 Settled design decisions

- **Wiring only.** `ComposedNet` and its configs describe the graph. The sub-networks are `nn.Module` instances the caller constructs as it does today, handed over in a `modules` mapping at the call site. No per-network config dataclasses (`MLPResNetConfig` and friends) are written here; that is a separate, orthogonal feature.
- **A named-node directed acyclic graph**, not a fixed stems-plus-trunk schema. Any acyclic wiring is expressible, a node may feed several consumers, and a one-node graph is behaviorally identical to the bare network, which is what makes existing generators re-expressible without changing their architecture.
- **A shape protocol of two methods, and the missing accessors get written.** `NetShape` is defined in `compose.py` and asks exactly two questions, `resolve_input_shape()` and `resolve_output_shape()`, each answered by a per-sample shape tuple. `MLPNet`, `MLPResNet`, `ConvNet`, `ConvResNet`, `TransformerNet`, `ChannelWiseTransformerNet` and `ScalableEfficientNet1D` are brought up to it, and the two int accessors `ScalableEfficientNet1D` has today are replaced rather than kept beside the new pair, so one convention holds across `dlk/nets/`. Shapes are never inferred by running a probe batch.
- **The replica split lives in `dlk`.** `ComposedNet.forward_partial` evaluates every node that does not transitively depend on a named input and returns them as a cache; the caller vmaps only the rest.
- **Multiple inputs are passed positionally.** A node with inputs `("stem_y", "stem_z")` is called as `module(stem_y_out, stem_z_out)`. `MLPResNet` and `MLPNet_MultIn` already flatten and concatenate their positional inputs (`dlk/nets/mlp.py:691-712`, `dlk/nets/mlp.py:220-259`), so the two-stem case needs no concatenation code in `ComposedNet`, and a single-input network such as an EfficientNet rejects a second input at build time.
- **Hidden-input edges are a second kind of edge.** `MLPResNet` and `ConvResNet` accept `h_kwargs` that inject a tensor into one residual block (`dlk/nets/mlp.py:691-745`, `dlk/nets/conv1d.py:303`). Modeling that as an edge is what lets an existing conditional generator be re-expressed as a one-node graph rather than redesigned.
- **Flat edges only.** Every edge between nodes carries a tensor of shape `(batch, size)`, that is a node output whose `resolve_output_shape()` has ndim 1. An EfficientNet stem runs with its head enabled and `num_classes` as its output width. A network that emits a feature map reports that honestly, as a 2D shape, and `ComposedNet` is the single place that rejects it on an edge. Feature-map edges, which would need a length-propagation rule per network type, are a follow-up.
- **`dlk` only.** This plan stops at the toolkit boundary. Adoption in any consuming application is deliberately out of scope and gets no section here.

### 1.3 Core principle

Composition is wiring and nothing else: a node is an already-built network, the graph adds no layers, no parameters and no initialization policy of its own, and every tensor that crosses an edge is a value one node returned and another node consumes unchanged.

The consequences are worth stating because they are what this plan then does not have to do. A composed net's parameter count is exactly the sum of its parts, so `get_parameters` (`dlk/nets/utils.py:163`) reports it with no special case. Its `state_dict` keys are `nodes.<node name>.<the network's own keys>`, so checkpointing needs no change. Any node can be lifted out and used alone, and any network that satisfies `NetShape` can be a node, including another `ComposedNet`, so the construction is closed under composition. Because `ComposedNet` never concatenates, flattens or reshapes anything itself, there is no second place where a shape convention could drift from what the networks already do, and the existing `forward` assertions inside each network stay the authority on what it accepts.

## 2. Terminology

- **Node**: one named entry in the graph, pairing a name, an already-built `nn.Module`, and the names its inputs come from.
- **Edge**: a dependency from a source (a node name or an external input name) to a consuming node. An ordinary edge delivers its tensor as a positional argument to the consuming module.
- **Hidden edge**: an edge that delivers its tensor as a keyword argument `h{index}` or `h_all` instead, which `MLPResNet` and `ConvResNet` route into one residual block rather than into the input layer.
- **External input**: a named tensor supplied by the caller rather than produced by a node, for example the observation and the latent vector of a conditional generator. Their declared order is the positional order of `ComposedNet.forward`.
- **Sink node**: a node whose output no other node consumes. A graph with exactly one sink has an unambiguous output node, which the config uses as a default.
- **Topological order**: an ordering of nodes in which every node follows all of its inputs. Computed once at construction, it is the order `forward` evaluates in.
- **Dependents of a name**: every node that transitively needs that external input or node, computed by forward reachability over the edges. Its complement is what can be evaluated without that input.
- **`vmap`**: `torch.vmap` adds a batch dimension to a function by tracing it once over batched tensors. It rejects operations that write into unbatched state, which is why a module with batch-normalization running statistics cannot be evaluated inside it in training mode.
- **Replica**: one of several latent samples drawn per observation. Replicas are the dimension a conditional generator is vmapped over.
- **Stem and trunk**: informal names for a node that consumes an external input directly, and for a node that consumes several stems' outputs.

## 3. `dlk/nets/compose.py`: the `NetShape` protocol

New file. Start with the protocol, since the rest of the module and the edits in sections 7 to 10 are written against it. It follows the `WeightedLayer` protocol already in `dlk/nets/utils.py:41-53` in style, and replaces the two int accessors `ScalableEfficientNet1D` already has with a single shape question.

```python
@runtime_checkable
class NetShape(Protocol):
    def resolve_input_shape(self) -> tuple[int | None, ...]: ...
    def resolve_output_shape(self) -> tuple[int | None, ...]: ...
```

Each answer is a per-sample shape with the batch dimension excluded, one entry per remaining dimension, and `None` for a dimension the network accepts at any extent, which is what `ScalableEfficientNet1D` means by `input_length=None`. So `MLPResNet(32, 3, ...)` answers `(32,)` and `(3,)`; `EfficientNetV1B0Minimal(input_channels=3, input_length=500, num_classes=64)` answers `(3, 500)` and `(64,)`; `ConvNet(input_channels=3, ...)` answers `(3, None)` because it constrains no length.

The ndim of a shape is the ndim of the tensor the network's own `forward` assertions are written against, minus the batch dimension. A network that documents a flat input, such as `MLPNet` or `TransformerNet`, answers with ndim 1 even though its `forward` also accepts a `(batch, 1, size)` tensor it flattens; a network with an explicit channel argument answers with ndim 2. The element count per sample is the product of the entries, or unknown when any entry is `None`, and that product is what section 4 validates edge widths against.

Two helpers belong here as well. `resolve_shape(module, config)` returns the `(input_shape, output_shape)` pair for one node, taking each from the explicit field of the node's config when it is set and from the protocol otherwise, and raising `TypeError` naming the node when the module satisfies neither. `modules_with_running_stats(net, names)` returns the node names in a sub-graph that hold `nn.modules.batchnorm._BatchNorm` instances, so a caller can assert that the region it is about to vmap is free of them.

## 4. `dlk/nets/compose.py`: `ComposedNet` and `create_composed_net`

`ComposedNet(nn.Module)` takes the node configs, the external input names, the output node name, and a `modules: Mapping[str, nn.Module]` giving one module per node. It stores the modules in an `nn.ModuleDict` named `nodes`, so parameter names, `state_dict` keys and `get_parameters` output all read as `nodes.<node name>.<...>`.

`__init__` validates the graph and raises `ValueError` naming the offending node for each of:

- a duplicate node name;
- a node name that collides with an external input name;
- an input naming neither a node nor an external input;
- a cycle;
- an output name that is not a node;
- a node that the output node cannot reach.

The last one matters beyond tidiness: DDP raises at the first backward pass when a wrapped module holds parameters that received no gradient, so a node wired into nothing has to fail at construction rather than at the first distributed step. A node whose module is a single-input network and that declares more than one input is rejected here too, by checking whether its `forward` accepts a variadic positional parameter.

It then computes and stores the topological order (Kahn's algorithm over the edge sets, both ordinary and hidden), and, when `validate_shapes` is on, checks every node whose inputs are all internal edges. Two things are checked there, and this is the only place either is enforced. Every source node's `resolve_output_shape()` must have ndim 1, that is exactly one entry, which is the flat-edge rule from section 1.2, so a source that emits a feature map is named and rejected at construction rather than reported as a width by the network itself. And the sum of the sources' widths must equal the consuming node's element count, with the check skipped when either side has a `None` entry, since an unknown extent is a shape the graph cannot arithmetic over. Edges from external inputs are not width-checked, because external shapes are names only in this design; a mismatch there surfaces from the consuming network's own `forward` assertion on the first batch, which is where `dlk` already puts that check.

`forward(self, *inputs: torch.Tensor, cache: Mapping[str, torch.Tensor] | None = None) -> torch.Tensor` binds its positional arguments to the declared external inputs in order, which is what makes a composed net a drop-in for the `g_net(y, z)` and `d_net(x, y)` call sites in `dlk/opt/train_gan.py:384-387`. It walks the topological order, skips any node already present in `cache`, calls each remaining module as `module(*positional_inputs, **hidden_kwargs)`, and returns the output node's tensor. It raises `ValueError` when a node is neither cached nor computable from what was supplied.

`create_composed_net(nodes, external_inputs, output, modules, *, validate_shapes=True, logger=None) -> ComposedNet` is the composing function the config in section 5 targets. It builds the `ComposedNet` and logs one line per node with its resolved input and output widths, in the style the existing factories log with.

`ComposedNet` itself implements `NetShape`: `resolve_output_shape()` delegates to the output node, and `resolve_input_shape()` delegates to the node that consumes the first external input. A composed net can therefore be a node inside another composed net.

## 5. `dlk/nets/compose.py`: `NodeConfig`, `HiddenEdge` and `ComposedNetConfig`

`HiddenEdge(NamedTuple)` has `source: str` and `block: int | Literal["all"]`, mapping to the `h{index}` and `h_all` keyword arguments the residual networks accept. `NodeConfig` is a frozen dataclass with `name`, `inputs: tuple[str, ...]`, `hidden_inputs: tuple[HiddenEdge, ...] = ()`, and the two optional overrides `input_shape: tuple[int | None, ...] | None = None` and `output_shape: tuple[int | None, ...] | None = None`, which mirror the protocol's two methods one for one. Both classes are wiring value objects in the spirit of `StageSpec` and `MBConvConfig` (`dlk/nets/efficientnet1d.py:14-41`), not typed argument sets for a torch target, so the `param_*` convention does not apply to them. The two overrides are the escape hatch for a node whose module does not satisfy `NetShape`, such as an `nn.Sequential(nn.AdaptiveAvgPool1d(1), nn.Flatten())` adapter or any module from outside `dlk`.

`ComposedNetConfig` is a typed argument set for `create_composed_net`, following `LinearConstCosineConfig` (`dlk/opt/scheduler.py:11-130`), which is the existing example of a config whose target is a `dlk` composing function rather than a torch constructor. Its stored fields are `nodes`, `external_inputs` and `output`, which are three of that function's parameters; `modules` belongs to the call rather than to the configuration and is passed at the call site, exactly as `dataset` is for `DataLoaderConfig` (`dlk/data/loader.py:44-59`).

Two fields resolve automatically, so the common graph needs neither spelled out.

```python
nodes: tuple[NodeConfig, ...]
param_external_inputs: InitVar[Sequence[str] | None] = None
param_output: InitVar[str | None] = None
external_inputs: tuple[str, ...] = field(init=False)
output: str = field(init=False)
```

`__post_init__` assigns both from their inputs or from a heuristic, and every stored value is concrete afterwards. `auto_external_inputs(nodes)` returns every input name that is not itself a node name, in order of first reference, which is deterministic and is the order `forward` will bind positionally; a caller who cares about that order states it. `auto_output(nodes)` returns the single sink node and raises `ValueError` listing the candidates when there is more than one. Both are public static methods, so a caller can use them without building a config.

`from_dict` maps `external_inputs` and `output` onto their `param_*` inputs through an explicit alias dict and raises `TypeError` on an unknown or missing key. It extends the pure alias map in one documented way: an entry of `nodes` given as a mapping is converted to `NodeConfig`, an entry of its `hidden_inputs` given as a mapping or pair is converted to `HiddenEdge`, and an `input_shape` or `output_shape` given as a list is converted to a tuple, so a graph can be written in YAML or JSON with no `param_` spelling and no manual construction. Entries that are already `NodeConfig` or `HiddenEdge` pass through unchanged, which keeps `ComposedNetConfig.from_dict(config.to_kwargs()) == config` true. `to_kwargs` is the standard one-liner over `fields(self)`.

## 6. `dlk/nets/compose.py`: replica partitioning

`dependents_of(self, name: str) -> frozenset[str]` returns every node that transitively depends on the given external input or node, by forward reachability over both edge kinds. It is cached per name on first use, since the graph is fixed at construction.

`forward_partial(self, *, exclude_dependents_of: str, **externals: torch.Tensor) -> dict[str, torch.Tensor]` evaluates, in topological order, every node that is not in `dependents_of(exclude_dependents_of)`, and returns the computed node outputs as a plain dict. It takes its external inputs by keyword rather than positionally, because the excluded input is exactly the one the caller does not have a single value for yet. It raises `ValueError` naming any external input that the nodes it must evaluate need and that was not supplied.

The pair composes into the replica pattern, where the cached tensors are unbatched constants closed over by the vmapped callable.

```python
cache = net.forward_partial(exclude_dependents_of="latent", features=y)
outputs = torch.vmap(lambda z_: net(y, z_, cache=cache))(z)
```

The docstrings state the two limits that are not enforceable in code. The cache is valid for one forward and its backward pass, since it holds activations that belong to one autograd graph; reusing it across optimizer steps backpropagates through a freed graph. And the split only avoids what the graph says is independent, so a module with running statistics inside the latent-dependent region still fails under `vmap`; `modules_with_running_stats` from section 3 is what a caller asserts on to catch that at setup time rather than at the first step.

The two replaced accessors were added in commit `6372185` and have no callers anywhere in the repository except that one line of `forward` and that docstring, so replacing them costs nothing and leaves `dlk/nets/` with a single shape convention. Section 14 records the missing length arithmetic as an observation.

## 11. Usage sketch

The motivating generator, built with `dlk` pieces only. Widths that cross an edge are derived, so the trunk's input width follows from the two stems and is checked at construction.

```python
from dlk.nets.compose import ComposedNetConfig, NodeConfig, create_composed_net
from dlk.nets.efficientnet1d import EfficientNetV1B0Minimal
from dlk.nets.mlp import MLPResNet

config = ComposedNetConfig(
    nodes=(
        NodeConfig("stem_y", inputs=("features",)),
        NodeConfig("stem_z", inputs=("latent",)),
        NodeConfig("trunk", inputs=("stem_y", "stem_z")),
    ),
    param_external_inputs=("features", "latent"),  # positional order of forward
)  # output resolves to "trunk", the single sink node

g_net = create_composed_net(
    **config.to_kwargs(),
    modules={
        "stem_y": EfficientNetV1B0Minimal(input_channels=3, input_length=500, num_classes=64),
        "stem_z": MLPResNet(32, 32, residual_blocks_sizes=[[32, 32, 128, 32]] * 2),
        "trunk": MLPResNet(96, 3, residual_blocks_sizes=[[96, 96, 384, 96]] * 4),
    },
)

x_gen = g_net(y, z)  # the call contract of dlk/opt/train_gan.py:384
```

The same generator with the latent injected into the trunk's first residual block instead of concatenated at its input, which is the shape an existing conditional generator has. Only the wiring changes, and the trunk is then built at width 64 rather than 96, with its first block sized to take the extra 32.

```python
nodes = (
    NodeConfig("stem_y", inputs=("features",)),
    NodeConfig("stem_z", inputs=("latent",)),
    NodeConfig("trunk", inputs=("stem_y",), hidden_inputs=(HiddenEdge("stem_z", block=0),)),
)
```

With replicated latents, the feature stem is evaluated once and only the latent-dependent part is vmapped.

```python
cache = g_net.forward_partial(exclude_dependents_of="latent", features=y)
x_gen = torch.vmap(lambda z_: g_net(y, z_, cache=cache))(z)  # (replicas, batch, 3)
```

## 12. Tests

New file `tests/nets/test_net_baselines.py`, written and green **before** any edit in sections 7 to 10. It freezes the forward output of `MLPNet`, `MLPResNet`, `ConvNet`, `ConvResNet`, `TransformerNet`, `ChannelWiseTransformerNet` and `EfficientNetV1B0Minimal` under `torch.manual_seed(0)` against constants stored in the file, each network small and on CPU, each network in `eval()` so batch-normalization statistics play no part. It carries a `if __name__ == "__main__":` entry point that regenerates and prints the constants, and a comment naming the `torch` version they were generated with, since the values are version and machine specific. The accessors added in sections 7 to 10 are pure readers, and these tests are what turns that claim into evidence.

## 17. Risks and edge cases

- The cache from `forward_partial` belongs to one autograd graph. Reusing it across optimizer steps backpropagates through a freed graph and raises; the docstring says so, and no code can enforce it.
- The split only avoids what the graph declares independent. A module with running statistics in the latent-dependent region still fails under `vmap`, which is what `modules_with_running_stats` exists to catch at setup.
- Node names are `state_dict` keys. Renaming a node in a config invalidates checkpoints written before the rename, silently as far as `torch.load` with `strict=False` is concerned.
- A `None` entry in a shape means the network accepts any extent there, so the element count is unknown and the edge width check is skipped rather than failed. The ndim check still applies, so a feature-map source is still rejected; what a `None` costs is the width comparison, which then lands on the consuming network's `forward` assertion at the first batch.
- External input shapes are names only, so a wrong observation shape is caught by the consuming network's own `forward` assertion on the first batch rather than at construction. That is consistent with where `dlk` puts shape checks, and it does mean the first failure arrives one step later than the internal edge checks do.
- `torch.compile` and the cache do not obviously mix: a dict argument whose contents change between calls invites graph breaks. Compiling the vmapped callable rather than `ComposedNet.forward` is the path to try first, using `CompileConfig` (`dlk/opt/compile.py:25`).
- The `auto_external_inputs` heuristic orders by first reference. A graph whose nodes are reordered in the config gets a different positional binding, which would silently swap the two arguments at a `g_net(y, z)` call site. The usage document states the order explicitly for anything that reaches a positional call site, and the config field exists exactly so it can be pinned.
- Rejecting a multi-input node by inspecting its `forward` for a variadic positional parameter is a signature heuristic. It is right for every current `dlk` network, and a module that takes several inputs without a `*args` parameter would be rejected wrongly; the explicit overrides on `NodeConfig` do not cover this, so such a module needs a thin wrapper.

## 18. Addendum: deviations and findings during implementation

Implemented 2026-09-21 to 2026-09-22, steps 1 to 9 of section 15. Step 10 is partially done: this addendum is written, the companion usage document is not.

### 18.1 One factual correction to the plan

Section 8 states that `ConvNet.resolve_output_shape` reports `(channels', None)` when the network has neither an output layer nor a dense layer, "because the network then emits a feature map". It does not. `ConvNet.forward` flattens the convolution stack unconditionally (`dlk/nets/conv1d.py:132`), before the dense layers, so the network returns a 2D tensor in every configuration and its per-sample shape always has ndim 1. Reporting `(channels', None)` would have been a false statement about the network and would have made section 4 reject a genuinely flat edge. The implemented answer is `(None,)`: one entry, width unknown, because the flattened width follows a sequence length the network does not constrain.

This changes one test in section 12. `test_edge_from_a_feature_map_source_is_rejected` names "a `ConvNet` without an output layer" as the feature-map source; that configuration is now an instance of the *other* half of the same test, the `None` entry that skips the width check. The rejection half uses `ConvResNet` without its residual MLP head, which genuinely returns `(batch, channels, length)` and answers `(channels', None)`. Both halves are in the test as written.

### 18.2 Deviations in the implementation

- **The multi-input check is stricter than section 4's.** The plan detects a variadic positional parameter on the module's `forward`; section 17 then records as a risk that a module with `forward(x, y)` would be rejected wrongly. The implementation counts positional capacity instead: variadic means unbounded, otherwise the parameter count must cover the node's declared inputs. The verdict is identical for every current `dlk` network, and that section 17 risk is retired rather than documented.
- **The edge width check covers positional edges only.** Section 4 says "the sum of the sources' widths must equal the consuming node's element count" without distinguishing the two edge kinds. A hidden edge enters one residual block rather than the input layer, so including it in the sum rejects correct graphs. Both edge kinds still get the ndim check, so a feature-map source is rejected wherever it appears.
- **`dependents_of` excludes the name itself, and `forward_partial` excludes it as well.** Section 6 defines the set as the nodes that depend on a name, which literally leaves that node out. Taken literally in `forward_partial`, passing a *node* name would cache that node's own output and the vmapped call would then reuse it, silently making every replica identical. `dependents_of` therefore stays literal and honest to its name, and `forward_partial` excludes the returned set together with that node.
- **`auto_external_inputs` counts hidden-edge sources.** Section 5 says "every input name that is not itself a node name" without settling whether hidden sources count. They must: otherwise a latent entering only through a hidden edge would never be declared external, while `ComposedNet` validates reachability over both edge kinds.
- **Three small additions not in the plan.** `HiddenEdge.keyword` maps a block index to `h{index}` or `h_all`, so that spelling has one home rather than being re-derived in `forward`; `NodeConfig.sources` returns positional then hidden sources, which the heuristics and every graph walk need; and `ComposedNet` rejects a *surplus* module, not only a missing one, because an extra key in the mapping is a misspelled node name more often than not.
- **`ComposedNetConfig.__post_init__` normalizes `nodes` to a tuple**, so a config built from a list still satisfies `from_dict(to_kwargs()) == config`.

### 18.3 Terminology: `ndim`, not "rank"

The plan and the first accessors written against it used "rank" for the number of tensor dimensions. That word is already taken twice in this repository: it is the DDP process index throughout `dlk/opt/distributed.py`, `monitor.py`, `profiler.py`, `train.py` and `train_gan.py`, and it is the linear-algebra rank in `dlk/loss/gaussian.py:13` (`svd_ranks`). A composed net under DDP is exactly where sections 4 and 16 lead, so "rank-one shape" and "rank 0" would have appeared in the same discussion.

The vocabulary is now `ndim`, matching `torch.Tensor.ndim` and `Tensor.dim()`, which `dlk/nets/` already uses 38 times, including in the `forward` assertions a few lines below each accessor. "1D" and "2D" are the adjectives for a sample's shape, and where a sentence is about the tuple itself it counts entries, which is what the code tests. "Order" was rejected: the plan already uses it about ten times for sequencing (topological order, positional order, order of first reference), and in a scientific-computing toolkit it also reads as order of accuracy. The change is applied throughout sections 1.2, 3, 4, 8, 9, 10 and 17 of this document and in every docstring of `dlk/nets/`.

### 18.4 Step-ordering artifacts

Two items in section 15 are scheduled before what they depend on, and both were resolved by a temporary shim that was removed on schedule rather than by reordering the work.

- Step 3 specifies `resolve_shape(module, config)` and `modules_with_running_stats(net, names)`, whose natural parameter types are `NodeConfig` (step 6) and `ComposedNet` (step 7). They were written against two structural protocols, `ShapeOverrides` and `NetNodes`, each carrying a `TODO` naming the step that retires it. Both were deleted on schedule, leaving `NetShape` as the module's only protocol, as section 1.2 intends.
- Step 6 asks for the config drift test, whose target `create_composed_net` does not exist until step 7. What could be checked without the target was checked in step 6 (no stored field carries the `param_` spelling, `modules` is not a stored field, the constructor takes exactly the three expected arguments), with a `TODO` carrying the deferred test's body. The subset assertion against the real signature, and the config skill's `check_config.py` run, both landed in step 7.

### 18.5 Version-pinned assumptions in the baseline constants

`tests/nets/test_net_baselines.py` freezes the forward output of all seven networks under `torch.manual_seed(0)` in `eval()` mode. The constants were generated with `torch 2.13.0+cu130` and verified bit-identical under `2.13.0+cpu`, which is the build CI installs via `uv sync --group cpu`; the maximum relative difference between the two builds was exactly zero across all seven cases.

The comparison uses two relative tolerances and nothing absolute. An untrained `EfficientNetV1B0Minimal` in eval mode decays its activations stage by stage, from a mean magnitude of 0.21 after the stem to 2.8e-9 at the head, so its output is around 1e-10 and a flat `atol=1e-6` would have accepted any change whatsoever to that network. `ELEMENT_RTOL = 1e-5` is taken per entry and `SCALE_RTOL = 1e-6` against the largest magnitude of the case, which is what covers entries near zero. Every case, EfficientNet included, was confirmed to reject a 1e-4 relative perturbation.

### 18.6 What the type checker and the formatter forced

- Once `modules_with_running_stats` took a real `ComposedNet`, basedpyright rejected the plain test double that had stood in for the node lookup. The tests now build real composed nets through a `_chain_net` helper, which is a better test anyway.

### 18.7 Test-infrastructure notes

- `auto_external_inputs` orders by first reference, and that order is the positional binding of `ComposedNet.forward`. Because `set - set` reorders between processes under string-hash randomization, a "simplification" to a set difference would silently swap the arguments at a `g_net(y, z)` call site from run to run. The implementation uses `dict.fromkeys`, which dedupes by hash and keeps insertion order, and a test runs the heuristic in subprocesses under two `PYTHONHASHSEED` values and requires both to agree with the in-process result. It costs 2.7 s, which is the price of making that regression fail loudly rather than flakily.
- Each test added in steps 5 and 8 was mutation-checked against the specific bug it guards, by patching the implementation in a scratch script and confirming the test fails: dropping the `enable_stem` branch, dropping the `enable_head` branch, hard-coding the input length, a `dependents_of` that splits nothing, and a numerically stale cache. All five were caught. The scratch scripts are not part of the repository.
- The smoke run of section 16 is implemented as two runnable examples rather than as a test fixture, at the user's direction, and the examples are then run by the suite. See 18.8.
