# Plan: Timers and Statistics for Training Loops

## Context

`train.py::train_epochs` and `train_gan.py::train_epochs` report only a single total training time (`time_train`) and a coarse `time/step = time_train / n_steps`. Neither separates the first epoch from the rest, even though the first epoch carries overhead the rest do not (dataloader worker spin-up, cudnn autotune, lazy CUDA init, `torch.compile` warm-up if enabled), which skews any average computed across all epochs including the first. `dlk/opt/utils.py`'s per-batch statistics compute mean/std via a running sum of `x` and `x^2` and then `variance = E[X^2] - E[X]^2`; this formula suffers catastrophic cancellation when the standard deviation is small relative to the mean, which is exactly the common case for per-step timing (consistent step durations). There is no median/min/max anywhere in the training logs.

Research conclusion: Welford's algorithm is the standard numerically stable streaming method for mean/variance (see Terminology below); it replaces the naive two-pass-in-one formula without changing its streaming, O(1)-memory-per-tag character.

An investigation of `tests/` and `README.md` (2026-09-19) confirmed: no test asserts on `time_train`, `time_step_mean/std`, `time_per_epoch`, `time_per_step`, `samples_per_second`, or any timing log message, only per-epoch `*_loss_mean` arrays are tested (DDP cross-rank equality and fixed-seed regression values). `README.md` documents `loss_mean/std`, `batch_dlog`, and `time_train`, but not the other timing fields. This gives freedom to change field names and formulas as long as `*_loss_mean` per-epoch arrays keep their current meaning. `train_diffusion.py` delegates entirely to `train.train_epochs` and needs no separate timing/stats change; it only needs an import-path fix (Section on `train_diffusion.py`/`profiler.py`).

A second investigation (2026-09-19) into moving and renaming the `train_dlog_*` family found two things the first investigation missed: `tests/opt/test_distributed.py` imports and calls these functions directly, and `TrainLog` is imported from `dlk.opt.utils` in four files, not three, `profiler.py` being the fourth. Both are folded into the per-file sections below.

**Settled design decisions:**

1. Per-epoch time measures the whole epoch body: checkpoint save, `validation_fn`, `train_batches`, LR-scheduler step, logging, `epoch_finalize_fn`, not just the batch-training portion.
2. Extended stats (median/min/max, beyond mean/std) apply to `time_step` only, not to loss or GAN loss/regularizer tags.
3. Mean/std switch to Welford's algorithm, with an exact two-round all-reduce for the distributed combine; no new `all_gather`-based primitive is needed for that part.
4. For the final training-run summary (not per-epoch progress logging): median combines across ranks as the mean of each rank's local median, called out with a note in the log since it is an approximation, not the exact global median; min/max combine across ranks via exact all-reduce (`MIN`/`MAX`); `samples/sec` gets the same statistic set as `time_step` (mean, std, median, min, max), computed per optimizer step over epochs `1..N-1` and reported for that same range; the first logged line (today `training time {x} s`) gains the first- and rest-epoch times, comma-separated, after the existing total.
5. Every duration value in these logs is formatted with the existing `format_seconds` helper, including `time_train` itself (switched from `{time_train:g} s`); `samples/sec` is a rate, not a duration, and keeps its existing `:g` formatting.
6. The `train_dlog_*` functions move from `utils.py` to a new `dlk/opt/monitor.py`, losing the `train_dlog` prefix: `batch_initialize`, `batch_update`, `batch_all_reduce`, `batch_finalize`, `epoch_initialize`, `epoch_update`, `epoch_finalize`, plus the new `summary_stats`. The `TrainLog` type alias moves with them since it is the schema these functions build. `format_seconds`, `EpochHookFn`/`BatchHookFn`, and the checkpoint functions stay in `utils.py`, unrelated to the monitoring dict family.
7. Call sites use a qualified import, `from dlk.opt import monitor` then `monitor.batch_initialize(...)`, not `from dlk.opt.monitor import batch_initialize`. Reason: `train.py`/`train_gan.py` already have parameters `epoch_initialize_fn`, `epoch_finalize_fn`, `batch_initialize_fn`, `batch_finalize_fn` (user-supplied hooks). Bare `epoch_initialize`/`batch_initialize`/etc. imported unqualified would sit one token away from those in the same function bodies, for example `batch_initialize_fn(batch_idx)` next to `batch_initialize(max_batches, ...)`, an easy misread in review or a future edit. The module prefix removes the ambiguity. `TrainLog` is imported directly by name since it is a type, not a call site, with no realistic collision.

**Core principle:** streaming (Welford) accumulation is used only where the data volume forces it, per-batch mean/std over what can be an unbounded number of batches; every other new statistic operates on a fully materialized local array, because it only ever needs to span one bounded pool (`time_step`/`samples_per_sec` over one training run's epochs `1..N-1`, or a single epoch's worth of `time_epoch` values), which always fits in memory outright. Consequence: one reusable function, `summary_stats`, handles first-epoch time, rest-epoch time, pooled `time_step`, and pooled `samples/sec` identically; there is no second streaming implementation and no per-metric distributed-combine logic to keep in sync.

## Terminology

- **Welford's algorithm**: an online method for computing mean and variance from a sequence of values one at a time, updating a running mean and `M2` (sum of squared deviations from the running mean) instead of accumulating raw sums of `x` and `x^2`. Avoids the catastrophic cancellation the naive `E[X^2] - E[X]^2` formula suffers when the standard deviation is small relative to the mean.
- **`M2`**: Welford's running sum of squared deviations from the current running mean; `variance = M2 / n`.
- **Parallel-axis theorem / pooled-variance combination**: the identity `sum((x_i - c)^2) = M2 + n * (mean - c)^2` for any constant `c`. Used here to combine each rank's local `(n, mean, M2)` into an exact global `(n, mean, M2)` with two all-reduces, instead of gathering every raw value across ranks.
- **Streaming vs. pooled statistics**: streaming statistics (mean, std) update one value at a time without keeping every value, needed because a training run can have an unbounded number of batches. Pooled statistics (median, min, max) need every value materialized at once; acceptable here because they are computed once, at the end of training, from a bounded pool.
- **Mean of per-rank medians**: the approximation used for a "global" median under DDP. Each rank computes its own local median from its own batches; the reported figure is the arithmetic mean of those per-rank medians. Exact when single-process; an approximation of the true dataset-wide median when distributed, since it does not account for how the value distribution differs between ranks. Logged with an explicit note whenever it is approximate.
- **rank / world_size / all-reduce**: process index; total number of processes; a collective operation every rank must enter together that combines a value elementwise across ranks (sum, min, max, ...). See `docs/features/2026.002__ddp__1-plan.md`'s Nomenclature section for the full DDP vocabulary this plan builds on.

## Mathematical appendix: statistics algorithms

Every statistics algorithm discussed while designing this feature, with status: implemented, superseded (was implemented before this plan, replaced by it), or discussed but not implemented (considered, rejected, recorded here so the reasoning is not lost).

### Superseded: naive two-pass-in-one mean/variance

Status: this was the formula in `utils.py::train_dlog_batch_update`/`_finalize` before this plan; removed, replaced by Welford's algorithm below. Given a stream of values `x_1, ..., x_n`, accumulate two running sums, `S1 = sum(x_i)` and `S2 = sum(x_i^2)`, then at the end `mean = S1 / n` and `variance = S2 / n - mean^2`, `std = sqrt(variance)`. Mathematically correct in exact arithmetic, but numerically unstable in floating point: when `std` is small relative to `mean`, `S2 / n` and `mean^2` are two large, nearly equal numbers, and their difference loses relative precision to catastrophic cancellation, occasionally producing a small negative "variance" before the square root. This is exactly the regime of per-step timing, where step durations are consistent (small `std`) but not tiny in absolute terms (`mean` around tens of milliseconds), which is why this plan replaces the formula rather than only extending it.

### Superseded: coarse whole-run time/epoch, time/step, samples/sec

Status: this was the final-summary formula in `train.py`/`train_gan.py` before this plan; removed, replaced by the first/rest-epoch breakdown and the pooled `time_step`/`samples_per_sec` statistics. `time_per_epoch = time_train / n_epochs`, `time_per_step = time_train / n_steps`, `samples_per_second = n_samples / time_train`, where `n_samples = n_steps * batch_size * world_size`. Correct as an average over the whole run, but blends the first epoch's one-time overhead into every other epoch's average, which is the core problem this plan exists to fix. `n_samples`'s formula is unchanged by this plan; it still feeds the pooled `samples_per_sec` below, just applied per pooled step instead of once over the whole run.

### Implemented: Welford's online algorithm for streaming mean/variance

`dlk/opt/monitor.py::batch_update`/`batch_finalize`. For each new value `x_n` (the n-th value seen in the stream), update a running mean and `M2` (running sum of squared deviations from the running mean) instead of the raw sums above:

```
delta  = x_n - mean_(n-1)
mean_n = mean_(n-1) + delta / n
delta2 = x_n - mean_n
M2_n   = M2_(n-1) + delta * delta2
```

initialized `mean_0 = 0`, `M2_0 = 0`. After all `n` values, `variance = M2_n / n`, `std = sqrt(M2_n / n)`. Never forms `S2` or `mean^2` directly, so it avoids the cancellation above. By induction, `M2_n` is algebraically identical to `S2 - n * mean_n^2` in exact arithmetic (same quantity as the naive formula's numerator), so both formulas compute the same variance in principle; they only differ in floating-point rounding behavior, which is the entire point. Reference: Welford (1962), Technometrics 4(3).

Convention carried over unchanged from the superseded formula: population (biased) standard deviation, dividing by `n`, not `n - 1` (no Bessel's correction). This plan does not revisit that choice.

### Discussed, not implemented: Chan/Golub/LeVeque pairwise combination of two Welford groups

Given group A with `(n_A, mean_A, M2_A)` and group B with `(n_B, mean_B, M2_B)`, both already Welford-accumulated separately (for example, two ranks' local statistics):

```
n_AB   = n_A + n_B
delta  = mean_B - mean_A
mean_AB = mean_A + delta * n_B / n_AB
M2_AB   = M2_A + M2_B + delta^2 * n_A * n_B / n_AB
```

For `R` groups, apply this pairwise, associative up to floating-point rounding: `((A combine B) combine C) combine ...`. To use this directly as the cross-rank combine, every rank needs every other rank's `(n, mean, M2)` triple, which needs an `all_gather` (not just an `all_reduce`) plus an `R`-way sequential combine loop on every rank. This is the "textbook" reference algorithm for combining streaming statistics across parallel workers, considered for `batch_all_reduce`'s and `summary_stats`'s cross-rank combine, and rejected in favor of the two-round all-reduce below, which needs no new `all_gather` primitive and no per-rank combine loop. The two algorithms are mathematically equivalent, both compute the exact global `M2`; they differ only in which collective operations and how many of them get there.

### Implemented: two-round all-reduce combine via the parallel-axis theorem

`dlk/opt/monitor.py::_distributed_combine_mean_m2`, shared by `batch_all_reduce` and `summary_stats`. Uses the identity `sum((x_i - c)^2) = M2 + n * (mean - c)^2` for any constant `c` (the parallel-axis theorem, also called König's theorem, for a sum of squared deviations).

Round 1, one all-reduce SUM over `R` ranks, gets the exact global `n` and global mean: pack each rank's `(n_r, n_r * mean_r)`, all-reduce SUM, then `n = sum(n_r)`, `mean = sum(n_r * mean_r) / n`.

Round 2: with the global mean now known identically on every rank (an all-reduce result is the same on every rank), each rank applies the parallel-axis identity with `c = mean` to get its own contribution to the global `M2`: `M2_r_corrected = M2_r + n_r * (mean_r - mean)^2`. A second all-reduce SUM combines these into the exact global `M2 = sum(M2_r_corrected) = sum over all ranks and all their values of (x - mean)^2`. Then `std = sqrt(M2 / n)`.

Needs exactly two collective calls total, not `R - 1` pairwise combines and no `all_gather`. Mathematically identical to the Chan et al. pairwise combine above (both give the exact global `M2`), derived via a cheaper communication pattern for this specific case: find the global mean first, in one shot across all `R` ranks, then correct, instead of combining ranks two at a time.

### Implemented: exact local median, min, max

`dlk/opt/monitor.py::batch_finalize`, per rank, from the fully materialized per-batch tensor stored for `extended_stats_tags`. `median`, `min`, `max` are order statistics of the rank's own sorted local sample (`torch.median`/`.min()`/`.max()`). Implementation note worth recording: `torch.median` on an even-length input returns the lower of the two middle order statistics, not their average, unlike `numpy.median`'s convention; this plan uses `torch.median`'s convention throughout and does not average the two middle values.

### Discussed, not implemented: exact global median via all-gather

Gather every rank's full local array (`all_gather` of the raw per-batch/per-pool values, not just summary scalars), concatenate into the true global pooled sample, compute its exact order statistic. Exact, but moves `O(n)` data across ranks (every raw value) where the mean/std/min/max combines above move only `O(R)` scalars; needs a new `all_gather`-based code path. Considered for `summary_stats`'s median and rejected on cost grounds in favor of the approximation below.

### Implemented: mean of per-rank medians (approximate distributed median)

`dlk/opt/monitor.py::summary_stats`. Each rank computes its own exact local median (previous section), then the reported figure is `mean_of_medians = (1 / R) * sum(median_r for r in ranks)`, one `all_reduce_sum_` of `R` scalars divided by `R`. Exact only when `R = 1` (single process) or when every rank's local median happens to coincide with the true global median; in general `mean_of_medians != true global median`, and the gap depends on how the value distribution differs between ranks. Logged with an explicit "(mean of per-rank medians)" note whenever `world_size > 1`, so the approximation is never silently presented as exact.

### Implemented: exact distributed min/max

`dlk/opt/monitor.py::summary_stats`, via `distributed.all_reduce_min_`/`all_reduce_max_`. Unlike the median, min and max are associative and distributive over a partition into ranks: `min(all values) = min(min_r for r in ranks)` and likewise for max, exactly, with no approximation, which is why min/max get an exact all-reduce while the median gets the cheaper mean-of-medians approximation instead of its own exact all-gather.

### Implemented: samples/sec as a derived, pooled statistic

`dlk/opt/train.py`/`train_gan.py`'s final-summary block. For each pooled per-step `time_step` value `t_i` (batch size `b`, world size `R`), define the per-step throughput sample `s_i = b * R / t_i`, then run `summary_stats` on the pool `{s_i}` exactly as on `{t_i}`; every combine rule above (Welford-exact mean/std, mean-of-medians, exact min/max) applies verbatim to this derived array, nothing new is needed.

Mathematical caveat worth recording, implicit in the design but not previously written down: this reports the mean of per-step throughputs, `mean(b*R/t_i)`, not the throughput of the mean step time, `b*R/mean(t_i)`. By the AM-HM inequality, for positive `t_i`, `mean(b*R/t_i) >= b*R/mean(t_i)`, with equality only when every `t_i` is identical. So `samples/sec ... mean` is always at least as large as `(batch_size * world_size) / (time/step ... mean)`, strictly larger whenever step times vary at all, which they always do in practice. This is a known, accepted property of averaging a reciprocal quantity, not a bug; it explains why the two numbers will never exactly match and both are legitimate, differently-defined figures.

### Per-batch: Welford mean/std, optional extended stats

`batch_initialize(n_batches, tags, extended_stats_tags=())`: for tags in `extended_stats_tags` (this plan passes `["time_step"]`), a full per-batch tensor is stored (needed for `median`) plus `{tag}_median/min/max` fields. Every tag still gets `{tag}_mean_n`, `{tag}_mean`, and a renamed `{tag}_m2` (replaces `{tag}_sq_mean`), plus `{tag}_std = None`.

`batch_update` switches the running update to Welford's formula:

```python
n = dlog[f"{tag}_mean_n"] + 1
delta = val - dlog[f"{tag}_mean"]
dlog[f"{tag}_mean"] += delta / n
delta2 = val - dlog[f"{tag}_mean"]
dlog[f"{tag}_m2"] += delta * delta2
dlog[f"{tag}_mean_n"] = n
```

NaN values are still excluded from the running stats (as today) and still written into the raw per-batch tensor for extended tags.

`batch_finalize`: `std = sqrt(m2 / n)` (population std, same convention as today's `variance = sq_mean - mean**2`). For each tag in `extended_stats_tags`, drop NaNs from the stored tensor and set `{tag}_median/min/max` from it. These stay local to this rank, no cross-rank combine here; this is the per-epoch/per-batch level. Cross-rank combining of median/min/max happens only in the new final-summary function below.

### Distributed combine for mean/std: `batch_all_reduce`

Naive sums combine via one all-reduce; Welford's `M2` does not, it needs the between-group cross term. Rather than adding an `all_gather` primitive, use the parallel-axis theorem in two sequential all-reduces, factored into a private helper shared with `summary_stats`:

```python
def _distributed_combine_mean_m2(
    n_local: torch.Tensor, mean_local: torch.Tensor, m2_local: torch.Tensor,
    device: torch.device | None,
) -> tuple[torch.Tensor, torch.Tensor, torch.Tensor]:
    if not distributed.is_distributed():
        return n_local, mean_local, m2_local
    # round 1: combine n and n * mean -> exact global n, global mean
    packed = torch.stack([n_local, n_local * mean_local]).to(device, torch.float64)
    distributed.all_reduce_sum_(packed)
    n_global, mean_global = packed[0], packed[1] / packed[0].clamp_min(1)
    # round 2: each rank's contribution to global M2 via the parallel-axis theorem
    delta = mean_local.to(device, torch.float64) - mean_global
    correction = m2_local.to(device, torch.float64) + n_local.to(device, torch.float64) * delta**2
    distributed.all_reduce_sum_(correction)
    return n_global, mean_global, correction
```

`batch_all_reduce` packs `(n, mean, m2)` for all tags into three length-`len(tags)` tensors and calls this helper once, batched across tags, same collective-call budget as today (two all-reduces per epoch instead of one, negligible). Docstring describes the two-round combine instead of "single all-reduce". Still no-op single-process, still called before `batch_finalize`. Extended-stat fields (`{tag}_median/min/max`) are untouched here, they remain per-rank local, per the scope decision above.

### New: `summary_stats`, the final cross-epoch, cross-rank combine

```python
def summary_stats(
    values: torch.Tensor, device: torch.device | None = None,
) -> dict[str, float]:
    """Compute mean/std/median/min/max for a local pool of values, combined across ranks.

    `mean`/`std` combine exactly (parallel-variance / Welford-consistent, see `_distributed_combine_mean_m2`). `median` combines as the mean of each rank's local median, an approximation the caller should note when logging under DDP. `min`/`max` combine exactly via `distributed.all_reduce_min_`/`all_reduce_max_`. No-op combine (single-rank stats returned as-is) when not distributed.
    """
```

One-shot computation on an already-fully-materialized local tensor, not a streaming accumulator, used only at the end of training and not per batch, so plain `torch.mean`/`torch.var`/`torch.median`/`torch.min`/`.max()` compute the local stats, then: mean/std via `_distributed_combine_mean_m2(n=[1], mean=[local_mean], m2=[local_var * n], device)` (reused, called with length-1 tensors); median via `distributed.all_reduce_sum_` of the local median divided by `distributed.get_world_size()`; min/max via `distributed.all_reduce_min_`/`all_reduce_max_` on the local min/max.

Returns `{"n": ..., "mean": ..., "std": ..., "median": ..., "min": ..., "max": ...}` (`n` = global count, informational). Handles a length-1 input, used for "first epoch time" where each rank has exactly one value: `mean` becomes the average of that one value across ranks, `min`/`max` the exact spread across ranks.

```python
        f"min {format_seconds(step['min'])}, max {format_seconds(step['max'])}"
    )
    if "samples_per_sec" in summary:
        sps = summary["samples_per_sec"]
        logger.info(
            f"samples/sec (epochs 1..{n_epochs - 1}): "
            f"mean {sps['mean']:g}, std {sps['std']:g}, "
            f"median {sps['median']:g}{note}, min {sps['min']:g}, max {sps['max']:g}"
        )
else:
    logger.info(
        f"training time {format_seconds(time_train)}, "
        f"first {format_seconds(summary['time_epoch_first'])}"
    )
    logger.info("only 1 epoch trained; no post-first-epoch time/step/samples-per-sec statistics")

epoch_dlog["summary"] = summary
```

Superseded post-implementation: see Addendum items 6-7. The summary-assembly logic shown above (`torch.cat`, repeated `monitor.summary_stats` calls, `epoch_dlog["summary"] = summary`) moved into `monitor.epoch_finalize`, and `time_epoch_first` ended up a full stats dict rather than the bare float shown here.

`time_train` itself switches from `{time_train:g} s` to `format_seconds(time_train)` for formatting consistency with the new fields; its value and meaning are unchanged, still the pre-existing total wall-clock including setup and the final post-loop checkpoint/validation call.

Returned dict schema addition: `epoch_dlog["time_epoch"]` (raw per-epoch tensor, this rank) and `epoch_dlog["summary"]` (nested dict of the combined final stats: `time_epoch_first`, `time_epoch_rest`, `time_step`, `samples_per_sec`, each a `{mean, std, median, min, max, n}` dict except `time_epoch_first`, a bare float). `time_epoch_rest`/`time_step`/`samples_per_sec` are omitted from `summary` when `n_epochs == 1`. The new top-level keys avoid colliding with the existing per-epoch arrays `epoch_dlog["time_step_mean"]`/`["time_step_std"]` (one value per epoch, from `DLOG_BASENAMES`), which are unchanged.

Edge cases: `n_epochs == 1` skips the rest/step/samples-per-sec lines and the corresponding `summary` keys entirely rather than emitting NaNs; `dataloader.batch_size is None` skips the `samples_per_sec` summary/log line, mirroring the existing `n_samples = 0` guard; a rest epoch with zero batches is guarded with `step_pool.numel() > 0` before pooling, and skips `time_step`/`samples_per_sec` the same way as the `n_epochs == 1` case if empty.

## Addendum: deviations and findings during implementation

1. **`summary_stats` pseudocode bug, caught before implementing.** The plan's code sketch for `summary_stats` called `_distributed_combine_mean_m2` with a hardcoded `n=[1]`, which only gives an exact combine for single-value pools (`time_epoch_first`). For the actual headline stats of this feature, `time_epoch_rest`, `time_step`, `samples_per_sec`, all multi-value pools, this would have silently understated the variance correction term (`n_local * delta**2` in the parallel-axis theorem), since it scales with the real local element count, not 1. Fixed by passing each rank's true `values.numel()` into the combine. Caught and confirmed before implementing, not found by a failing test after the fact.
2. **Ship-gate test targets the fix directly.** `tests/opt/test_monitor.py::test_two_process_summary_stats_matches_hand_computed_references` uses deliberately unequal per-rank pool sizes (23 vs. 29) specifically so a `n=1` placeholder would fail the exactness assertion; a same-size-pools test would not have caught the bug (the combine degenerates to a correct-looking unweighted average when both ranks contribute equally). `test_two_process_batch_all_reduce_exactness_adversarial` does the same for `batch_all_reduce` (37 vs. 41), plus adversarial magnitudes (mean ~1e6, std ~1e-3) to exercise the numerical-stability motivation for the whole Welford rewrite, not just the exactness of the combine arithmetic.
3. **No other deviations from the plan, as of this initial implementation pass.** File layout, function names, log line formats, the `epoch_dlog["summary"]` schema, and all import migrations (`train.py`, `train_gan.py`, `train_diffusion.py`, `profiler.py`, `tests/opt/test_distributed.py`) match the plan as written. Further deviations, found during later review and follow-on refactoring on the same branch, are recorded in items 5-9 below.
4. **Verification outcome (2026-09-19).** `make format-check` and `make lint` clean; `make testq` 209 passed, up from a 202-test baseline (7 new: 4 single-process `test_monitor.py` cases, 2 two-process ship-gate tests, plus the migrated `test_distributed.py` cases counted under their existing names). Manual sanity runs (single-process `n_epochs=1` and `n_epochs=4`, plus 2-process gloo) confirmed the new log lines, the `n_epochs == 1` no-stats path, and the "(mean of per-rank medians)" note appearing only under DDP. `grep -rn "train_dlog"` across the repo returns only this plan document's own historical narration, zero stragglers in code. Nothing has been committed (per this repo's CLAUDE.md rule); changes sit in the working tree on branch `next`, pending review.
5. **`epoch_dlog["batch_dlog"]` unbounded retention (flagged as "Not addressed here" in Unrelated improvements above) resolved.** `epoch_update` used to append the entire per-epoch `batch_dlog` (including any `extended_stats_tags` per-batch tensor, e.g. `time_step`, one full tensor per epoch) into `epoch_dlog["batch_dlog"]`, retained for the whole training run regardless of whether anything downstream read it back; `train.py`/`train_gan.py` in fact only ever read `bd["time_step"]` out of that list, never the rest of each per-epoch dict. Resolved by removing `epoch_dlog["batch_dlog"]` entirely and adding an opt-in `raw_tags: Sequence[str] = ()` parameter to `monitor.epoch_initialize`/`epoch_update`: only tags a caller explicitly names (`train.py`/`train_gan.py` name just `"time_step"`) get collected into a plain per-epoch list (`epoch_dlog["time_step"]`), rather than the whole per-epoch dict with all its Welford scratch state riding along. `epoch_initialize`'s `save_list: bool` parameter (unused, always defaulting `True` at every call site, left unrenamed by this plan's original migration) was also renamed to `extended_stats_tags: Sequence[str] = ()`, mirroring `batch_initialize`'s existing pattern: only tags named there get a materialized per-epoch tensor, other tags stay `None` and are not tracked across epochs at all.
6. **`monitor.epoch_finalize` absorbed the final-summary computation this plan had assembled inline in `train.py`/`train_gan.py`** (the "Final summary" code block earlier in this document). `train.py` and `train_gan.py` had byte-for-byte identical `time_epoch`/`time_step`/`samples_per_sec` pooling logic (`torch.cat`, repeated `monitor.summary_stats` calls, `epoch_dlog["summary"] = summary`); this moved into `monitor.epoch_finalize`, which now takes `n_epochs`, `device`, and `global_batch_size` and builds `dlog["summary"]` itself from `dlog["time_epoch"]` and, when present, the `raw_tags` list `dlog["time_step"]` (item 5). Both training loops now compute `global_batch_size` once (reused for the existing `n_samples` calculation too) and call `monitor.epoch_finalize(...)`, keeping only the `logger.info(...)` calls from the original "Final summary" block. `n_epochs` and `global_batch_size` are passed in rather than derived inside `epoch_finalize`, by explicit preference during review: `n_epochs` is already known at the call site, and `global_batch_size` is already computed there as a byproduct of `n_samples`.
7. **`time_epoch_first`'s type deviates from what this plan documented.** The "Final summary" code sketch and the "Returned dict schema addition" paragraph both describe `time_epoch_first` as "a bare float" (`first["mean"]`); `train_gan.py`'s implementation matched that, but `train.py`'s implementation instead stored the full `summary_stats` dict (`{n, mean, std, median, min, max}`), an undocumented divergence between the two files surfaced during a later `train_gan.py` review. Resolved in favor of the full dict for both files and `README.md`, since it preserves cross-rank spread in the first epoch's time even though each rank contributes only one value to it, consistent with every other `summary` entry.
8. **A regression in whole-epoch-body timing (settled design decision 1), introduced and caught during a later renaming/simplification pass on `train.py`, before it was reviewed.** The `time_epoch` stopwatch-stop assignment was moved to before `monitor.epoch_update`/`logger.info`/`epoch_finalize_fn` in the per-epoch loop body, so it stopped covering logging and the `epoch_finalize_fn` hook, contradicting decision 1 and the `README.md` schema description ("covering the whole epoch body ... logging"). The same pass also narrowed `epoch_initialize`'s `extended_stats_tags` argument to `["time_epoch"]` only, silently dropping per-epoch history for `loss_mean`/`loss_std`/`time_step_mean`/`time_step_std` (those `epoch_dlog[tag]` entries became `None`); caught by `test_train_single_process_regression.py` and `test_train_distributed.py` failing with `TypeError`/`AttributeError` on `None`, not by inspection. Both fixed: `extended_stats_tags` restored to cover every epoch-level tag, and the `time_epoch` stopwatch-stop plus the single `monitor.epoch_update` call moved back to after `epoch_finalize_fn`, so `epoch_update` remains the one place that copies every epoch-level tag, including `time_epoch`, out of `batch_dlog`.
9. **Naming: `DLOG_BASENAMES`/`dlog_tags` renamed to `MONITOR_BASENAMES`/`monitor_tags`** in both `train.py` and `train_gan.py`, replacing the names this plan introduced, for consistency with the `monitor` module qualifier established in settled design decision 7.
