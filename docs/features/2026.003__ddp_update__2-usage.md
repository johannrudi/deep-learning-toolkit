# Training with DDP using `dlk.opt.distributed`

`dlk` trains across processes with **DDP** (`DistributedDataParallel`): a launcher starts one process per device, each process holds a full replica of the model and trains on its own shard of the data, and gradients are averaged across replicas during the backward pass. Each process must discover its **rank** (its index among the processes), bind itself to one device, receive a distinct shard, and enter every collective operation the other processes enter. A process that skips a collective does not error; it hangs until the timeout expires.

`dlk.opt.distributed` keeps all of this opt-in. Every helper checks for an initialized process group first: without a launcher, `wrap_net` returns the model untouched, `sampler_create` returns `None`, and `barrier` returns immediately. **The same script runs single-process, unchanged, when launched without torchrun.** Going distributed is the six code changes below plus a launch command.

This guide assumes you have trained a model on a single device and can read a Slurm job script. It supersedes [2026.002__ddp__2-usage](2026.002__ddp__2-usage.md).

> [!NOTE]
> **Requires torch >= 2.11.** The module uses `torch.accelerator` for device binding and `torch.distributed.get_default_backend_for_device` for backend selection; neither exists in older releases.

## Preparing the application

### Step 1: Open a distributed session

`session` reads the launcher's environment, creates the process group, and destroys it on every path out of the `with` block.

```python
from dlk.opt import distributed

with distributed.session() as ctx:
    device = ctx.device
    ...  # Steps 2 to 5 happen inside this block
```

`ctx` is a frozen `DistributedContext` carrying `rank`, `local_rank`, `world_size`, `local_world_size`, `device`, `num_threads`, `is_main`, and `is_distributed`. Detection runs in order: torchrun variables (`RANK`, `WORLD_SIZE`), then the Slurm fallback (`SLURM_PROCID` with exported `MASTER_ADDR` and `MASTER_PORT`), and with neither present a single-process context without a process group. Each process logs the path it took:

```text
INFO:dlk.opt.distributed.initialize:distributed run, rank 0/2, local_rank 0/2, device cpu, backend gloo, num_threads 8
INFO:dlk.opt.distributed.initialize:single-process run, device cpu, num_threads 16
```

Prefer the `with` block over calling `initialize()` and `finalize()` yourself. When one rank crashes, `session` skips the closing barrier and the survivors tear down immediately; a hand-written pair leaves them in that barrier until the collective timeout expires, 1800 seconds by default.

### Step 2: Seed the random generators

Seed inside the session, and keep the base seed in a variable because Step 5 needs it.

```python
distributed.seed_random_generators(base_seed)
```

The helper seeds `random`, numpy, and torch with `base_seed + rank`, so per-rank draws such as latent samples and augmentation noise differ across processes. Identical seeds make every process generate the same "random" data, which quietly wastes most of the run.

### Step 3: Rank-suffix the log files

`dlk/mgmt/log.py` opens log files with `filemode="w"`, so ranks writing one file name truncate each other's output. Give each rank its own file:

```python
log_name = name if not ctx.is_distributed else f"{name}_rank{ctx.rank}"
```

Single-process runs keep their unsuffixed names, so existing workflows are untouched.

### Step 4: Wrap the models

Move the model to the device, then wrap it; `wrap_net` requires the model to reside on `device` already.

```python
net = distributed.wrap_net(net.to(device), device)
```

For GAN training, wrap the generator and discriminator independently and pass `broadcast_buffers=False` for the discriminator: it runs several forward passes per batch, and each one would otherwise pay a buffer synchronization.

```python
g_net = distributed.wrap_net(g_net.to(device), device)
d_net = distributed.wrap_net(d_net.to(device), device, broadcast_buffers=False)
```

Keep `find_unused_parameters=False` and `static_graph=False`, the defaults; the train loops are written for them.

### Step 5: Shard the data

Create the sampler with the context and the base seed, then thread it into the DataLoader:

```python
sampler = distributed.sampler_create(dataset, ctx=ctx, shuffle=shuffle, base_seed=base_seed)
if sampler is not None:
    dataloader_kwargs["sampler"] = sampler
    dataloader_kwargs["shuffle"] = False
```

The base seed matters: all ranks compute the same shuffle permutation and slice their own shard from it, so a rank-offset seed trains some samples twice per epoch and others never. `shuffle=False` on the DataLoader matters too: shuffling now belongs to the sampler, and PyTorch rejects the combination with `ValueError: sampler option is mutually exclusive with shuffle`. That is the friendly failure; forgetting the sampler entirely fails silently, with every rank training on the full dataset.

Passing `ctx` makes the sharding explicit and turns one setup error into a message: a context reporting `world_size > 1` without a live process group raises `RuntimeError: context reports world_size N, but no process group is initialized`. With `ctx` given, a sampler always comes back; a single-process context shards into one piece.

> [!NOTE]
> The train loops (`dlk.opt.train`, `dlk.opt.train_gan`, `dlk.opt.train_diffusion`) are rank-aware internally and take no new arguments: they call `set_epoch` on the sampler each epoch, checkpoint and validate on the main process only, hand `validation_fn` the unwrapped model, and reduce the reported loss statistics exactly across ranks. Do not add rank checks around them.

### Step 6: Finish on the main process

Prediction, evaluation, and plotting belong outside the session, on one rank:

```python
with distributed.session() as ctx:
    ...  # training

if ctx.is_main:
    evaluate(distributed.unwrap_net(net))
```

Leaving the `with` block synchronizes the ranks and destroys the process group, so no rank exits while another still trains. `unwrap_net` returns the inner model from a DDP wrapper and any other model unchanged, so the line is safe single-process too.

## Launching the run

### Step 7: Launch with torchrun

torchrun spawns the processes and sets the environment variables Step 1 reads. On one node with four devices:

```sh
uv run torchrun --standalone --nproc-per-node=4 run.py
```

Every rank logs its own lines, so expect each message multiplied by the world size. Identical loss values across ranks are the cross-rank reduction from the note above at work:

```text
INFO:dlk.opt.distributed.initialize:distributed run, rank 0/2, local_rank 0/2, device cpu, backend gloo, num_threads 8
INFO:dlk.opt.distributed.initialize:distributed run, rank 1/2, local_rank 1/2, device cpu, backend gloo, num_threads 8
INFO:dlk.opt.train.train_epochs:epoch    0, loss mean 3.434223e+00 std 1.560e+00
INFO:dlk.opt.train.train_epochs:epoch    0, loss mean 3.434223e+00 std 1.560e+00
```

See the [torchrun documentation] for options beyond these.

### Step 8: Launch under Slurm

Run torchrun inside the allocation and derive the process count from the allocation, so the two cannot drift apart:

```sh
#SBATCH --nodes=1
#SBATCH --ntasks-per-node=1
#SBATCH --cpus-per-task=16
#SBATCH --gpus-per-node=4

srun torchrun --standalone --nproc-per-node=$SLURM_GPUS_PER_NODE run.py
```

Size `--cpus-per-task` from the ranks and their DataLoader workers. One core per rank is the floor, below which the rank processes time-slice and their GPUs idle between kernel launches; `num_workers` adds one process per worker per rank. The directive counts per Slurm task, so here all four ranks share the 16 cores, while the one-task-per-rank layout below gives each rank its own count.

Multi-node jobs need a **rendezvous**, the ranks finding each other across nodes. Point every node at a port on the first node of the allocation:

```sh
head_node=$(scontrol show hostnames "$SLURM_JOB_NODELIST" | head -n 1)
srun torchrun \
    --nnodes=$SLURM_JOB_NUM_NODES \
    --nproc-per-node=$SLURM_GPUS_PER_NODE \
    --rdzv-backend=c10d \
    --rdzv-endpoint=$head_node:29500 \
    run.py
```

Where torchrun is unavailable, run one Slurm task per process. The job script must export the rendezvous address:

```sh
#SBATCH --nodes=2
#SBATCH --ntasks-per-node=4
#SBATCH --gpus-per-node=4

export MASTER_ADDR=$(scontrol show hostnames "$SLURM_JOB_NODELIST" | head -n 1)
export MASTER_PORT=29500
srun python run.py
```

This path derives the ranks from `SLURM_PROCID`, `SLURM_LOCALID`, and `SLURM_NTASKS`, and the per-node process count from `SLURM_NTASKS_PER_NODE` when the job requested `--ntasks-per-node`, otherwise from `SLURM_TASKS_PER_NODE`. `srun` forwards the exported environment by default with `--export=ALL`. (Check your site's default!)

## Checking that a run is really distributed

Optional; read this the first time an application goes distributed, or when two ranks are no faster than one. Both checks are **collectives**, so every rank must call them or the run hangs, and both are debugging aids to delete afterwards.

`check_batch_ranks_differ` reports whether the ranks drew different samples. It gathers one checksum per rank and returns whether all are distinct; `False` means every rank trains on the same data, which turns a four-way run into four copies of one gradient and points at a missing sampler in Step 5.

`check_net_replica_drift` reports the largest parameter difference from rank 0 over all ranks: `0.0` for a healthy DDP run, anything else for replicas that diverged, typically from a rank-dependent initialization or an optimizer step taken outside DDP's synchronization. Pass `include_buffers=True` to compare batch-norm running statistics as well.

```python
batch = next(iter(dataloader))[0].to(ctx.device)
print(f"[rank {ctx.rank}] batches differ: {distributed.check_batch_ranks_differ(batch)}")
print(f"[rank {ctx.rank}] replica drift: {distributed.check_net_replica_drift(net)}")
```

```text
[rank 0] batches differ: True
[rank 1] batches differ: True
[rank 0] replica drift: 0.0
[rank 1] replica drift: 0.0
```

A checksum can collide in principle, so `False` from the batch check is conclusive while `True` is strong evidence.

## Controlling the thread budget

Optional; read this on CPU nodes, or when a multi-process run is slower than a single process. `OMP_NUM_THREADS` controls the intra-op threads; the toolkit never sets the count and only records what it finds, as `ctx.num_threads` and in the initialization log line.

Give each rank an even split of the node: the usable cores divided by the ranks on the node, which `ctx.local_world_size` reports. Four ranks on a 64-core node get 16 threads each; four ranks with 64 threads each thrash the node. On one node:

```sh
OMP_NUM_THREADS=16 uv run torchrun --standalone --nproc-per-node=4 run.py
```

Under Slurm, derive the value from the allocation. With one task per rank, the task's CPU count is the rank's budget; with torchrun inside a single task, divide by the ranks it spawns:

```sh
export OMP_NUM_THREADS=$SLURM_CPUS_PER_TASK                            # srun python run.py
export OMP_NUM_THREADS=$((SLURM_CPUS_PER_TASK / SLURM_GPUS_PER_NODE))  # srun torchrun ...
```

> [!WARNING]
> When `OMP_NUM_THREADS` is unset, **torchrun exports `OMP_NUM_THREADS=1`**, and one thread per rank leaves most of a CPU node idle. Set the variable explicitly in the launch command, and verify with `torch.get_num_threads()`, `ctx.num_threads`, or the `num_threads` in the initialization log line.

## Things worth knowing

**Devices other than CUDA.** Device binding goes through `torch.accelerator`: a CUDA node picks `cuda:{local_rank}` with the nccl backend, an Intel GPU node picks `xpu:{local_rank}` with xccl, and everything else runs on CPU with gloo. Force a backend with `session(backend="gloo")`. MPS is treated as a gloo device deliberately; it has no per-process communicator.

**Shard padding.** `DistributedSampler` pads shards to equal length by repeating samples, because a rank that runs out of batches early leaves the others deadlocked in a collective. The repeats bias epoch metrics slightly; pass `drop_last=True` to `sampler_create` to drop the trailing samples instead.

**DataLoader workers.** `multiprocessing_context="fork"` is unsafe once CUDA is initialized; under DDP use `"spawn"` or `num_workers=0`. Workers count per rank: 4 ranks with 8 workers each start 32 loader processes, which compete with the threads from the section above.

**Resuming from a checkpoint.** Checkpoints are written by the main process from the unwrapped model, so they never contain `module.`-prefixed keys. Every rank loads the same file onto its own device, preferably before wrapping: `epoch = checkpoint_load(path, net, optimizer=optimizer, map_location=ctx.device)`.

**Changing your mind.** There is nothing to switch off. Run the same script without torchrun, or without an exported `MASTER_ADDR`, and it takes the single-process path: no process group, unsuffixed logs, `sampler_create(dataset)` returning `None`.

## Fixing common issues

**`ValueError: sampler option is mutually exclusive with shuffle`.** The DataLoader got both a sampler and `shuffle=True`. Set `shuffle=False` on the DataLoader and pass the shuffling intent to `sampler_create` (Step 5).

**`RuntimeError: local rank 2 needs at least 3 cuda devices, but only 2 are visible`.** More processes were started than devices are visible to them, usually `--nproc-per-node` exceeding the GPUs per node or a stale `CUDA_VISIBLE_DEVICES`. Match the process count to the devices, or widen the mask.

**`RuntimeError: context reports world_size 4, but no process group is initialized`.** `sampler_create` received a multi-process context outside a live session, so the shards would never be recombined. Move the call inside the `with distributed.session()` block.

**The job hangs at the end instead of exiting.** One rank left a collective the others are still waiting in. If the ranks were torn down with a hand-written `initialize`/`finalize` pair, switch to `session`, which skips the closing barrier while unwinding an exception.

**Two ranks are no faster than one.** Check the data first with `check_batch_ranks_differ`, then the threads with `torch.get_num_threads()`. Two ranks that each grabbed the whole node's cores is the common cause on CPU; set `OMP_NUM_THREADS` to an even split (see [Controlling the thread budget](#controlling-the-thread-budget)).
